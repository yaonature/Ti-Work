## 1. 产品重新定义

Ti Work 后续不是继续做“功能很多的 AI 桌面工具”，而是做一套面向企业员工真实日常工作的桌面办公平台。

目标形态：

- 员工可以用它处理文件、网页系统、知识库、流程任务、数据库、日常文档与表格类工作
- 平台可以沉淀企业知识、团队经验、岗位 SOP、员工技能与常见执行模板
- 平台可以把“单次会话”升级成“可复用的业务执行能力”
- 平台逐步具备自修复、自优化、自进化能力

一句话定义：

**Ti Work = 企业员工的 AI 办公操作台 + 企业知识 / 流程 / 技能沉淀平台。**

---

## 2. 当前问题

当前产品不是能力绝对不足，而是存在三个核心问题：

1. **安装版尚未闭环**：免安装验证已通过，但正式安装版还没有做到“安装阶段就把 Hermes 网关准备好，安装后首启即可对话”
2. **能力太散**：左侧一级菜单过多，用户无法快速识别主路径
3. **缺少闭环**：文件、浏览器、记忆、数据库、流程、审计还没有串成企业办公闭环

因此后续路线必须先做：

- 底座稳定
- 菜单收口
- 核心工作闭环
- 组织沉淀闭环

---

## 3. 左侧菜单目标结构

当前侧边栏入口太多，开发者视角过重。后续必须把前台菜单做成：

**稳定通用骨架 + 行业工作包命名映射 + 角色裁剪 + 个人习惯微调。**

说明：

- 本章是早期面向“通用办公产品骨架”的探索性菜单规划。
- 随着最新产品边界明确为“`Ti OPC` 承接统一前台与云端主服务，桌面端收束为执行增强层”，桌面端最终左侧菜单以文末新增的“桌面端最终能力边界与左侧菜单收口”章节为准。
- 因此，本章的 `工作台 / 业务 / 文档 / 知识 / 协作 / 管理` 六槽位设计，不再作为桌面端最终一级菜单实施标准。

这里的“菜单”指的是用户前台看到的产品菜单，而不是底层技术能力分组。  
也就是说，前台菜单必须是非技术性的工作语言，不能把 `会话 / 执行 / 多智能体 / MCP / 血缘` 这类术语直接暴露给最终办公用户做一级导航。

### 3.1 通用产品骨架的目标一级菜单

前台一级菜单固定为 6 个槽位，长期不随行业频繁变化：

| 菜单 | 核心定位 | 主要承载内容 |
|---|---|---|
| 工作台 | 今日工作入口 | 今日待办、提醒、最近工作、今日摘要、快捷动作 |
| 业务 | 当前真正要处理的工作 | 业务任务、任务助手、检索、分析、专项工作 |
| 文档 | 各类材料与输出物 | 文档起草、审阅、比对、文件处理、模板、报表 |
| 知识 | 个人与组织沉淀 | 知识库、规则、经验、工作画像、模板偏好 |
| 协作 | 流转、审批与团队配合 | 任务流转、审批、协同、流程、自动化 |
| 管理 | 治理与运营 | 权限、安全、审计、日志、分析、运行状态 |

底部固定：

- 设置
- 帮助 / 文档

说明：

- `管理` 默认按角色显示，不必对所有普通用户展开
- `搜索` 是全局入口，不计入一级菜单
- 行业包主要改变的是 `业务` 与 `文档` 的命名和内容，`工作台 / 知识 / 协作 / 管理` 尽量保持稳定

- 只在管理员、高级用户或专业模式中显式暴露必要的技术细节

### 3.6 菜单收口与实施原则

- 一级菜单长期固定为 `工作台 / 业务 / 文档 / 知识 / 协作 / 管理`
- 行业包主要通过“菜单别名 + 首页模块 + 二级菜单 + 默认模板/知识源/流程”体现差异
- 不再继续新增一级菜单
- 实验能力默认不进入一级导航
- 二级功能放入域页面内部 tab / 面板
- 菜单首先按“办公任务”组织，而不是按“技术模块”组织
- 开发实施时，优先改导航分组与命名，不要求第一阶段重写全部页面
- `管理` 为角色可见项，普通用户可按需要弱化或默认隐藏

#### 3.7.3 第二阶段整理动作

第一阶段完成后，再进入第二阶段收口：

1. 为通用办公包补齐统一的二级导航名称
2. 为律所、财务、人事等行业包做前台别名映射
3. 把页内 tab、标题、按钮文案也逐步从技术术语替换成业务术语
4. 将 `任务 / 待办 / 多智能体 / 编排` 在视觉上收敛为同一协作域体验
5. 将 `记忆 / 技能 / 档案 / 规则 / Obsidian / 工作画像` 逐步整成统一知识域

#### 3.7.4 建议的研发实施顺序

建议按以下顺序推进，避免一次性改动过大：

##### A. 第一步：只改导航配置和名称

- 修改侧边栏分组
- 修改显示名称
- 调整 icon 和排序
- 不改现有路由文件

##### B. 第二步：补二级入口与页头名称

- 页面标题与面包屑改名
- 页内 tab 与操作按钮改成业务术语
- 把重复入口合并到统一二级菜单

##### C. 第三步：加入行业别名与工作模式切换

- 通用办公包名称先上线
- 再接入律所、财务、人事等行业工作包别名
- 菜单名称、首页卡片、默认模板随工作模式切换

##### D. 第四步：再做深层页面重构

- 只有在导航收口稳定后，才重做复杂页面
- 避免一边改路由、一边改菜单、一边改页面信息架构，导致工作量失控

#### 3.7.5 当前阶段明确不做的事

为了保证收口效率，这一步先不做：

- 不重写全部页面内部逻辑
- 不强制修改所有路由路径
- 不一次性做完所有行业包的完整首页
- 不把实验能力、调试能力、研发能力重新抬成一级菜单

#### 3.7.6 本节作为开发实施依据的使用方式

后续菜单导航改版开发，必须以本节为基准：

1. 先查当前路由归属到哪个一级/二级菜单
2. 再判断该入口是保留、改名、归并还是弱化
3. 若新增页面，必须先回答它属于：
   - 工作台
   - 业务
   - 文档
   - 知识
   - 协作
   - 管理
4. 若无法明确归属，说明信息架构尚未设计清楚，不能直接加入口

## 4. 总实施路线

产品按 `P0 -> P1 -> P2 -> P3 -> P4` 推进，每个阶段都要有明确产物、功能边界与验收标准。

## 5. P0：Hermes 首装与执行底座稳定

### 5.0 当前状态

P0 已完成第一阶段闭环：

- 免安装版 / `win-unpacked` 已可自动拉起 Hermes 网关
- `8642` 健康检查可通过
- 模型列表可正常返回
- 首条消息已可真实发送并收到回复

但对正式交付来说，P0 还差最后一个必须完成的版本：

- **安装版闭环**

也就是：用户在安装 Ti Work 的过程中，就已经把 Hermes 网关相关依赖、运行目录、配置骨架一并准备好；安装成功后首次打开应用，要么直接可对话，要么明确提示配置 API Key，配置完成后立即可对话。

### 5.1 阶段目标

让桌面端正式安装版真正达到：

- 安装过程中就完成 Hermes 网关所需资源与目录准备
- 用户安装成功后第一次打开即可进入可用状态，而不是再经历长时间自举等待
- 若未配置模型 API Key，首启必须给出清晰、唯一、可完成的配置引导
- 用户完成 API Key 配置后，可立即稳定完成第一条消息

### 5.2 本阶段必须完成的功能

1. **安装版后端稳定启动**
   - 不依赖用户机器外部 `node.exe`
   - 使用安装包自身 runtime 拉起本地后端

2. **安装过程中完成 Hermes 预装**
   - 安装包内置 Hermes 固定版本资源
   - 安装程序在安装阶段完成 Hermes 工作目录准备
   - 安装程序在安装阶段完成 gateway 所需依赖与运行时初始化
   - 安装结束时，本地已具备可启动 Hermes 网关的最小完整环境

3. **首启即用 / 首启即配**
   - 若本地已有有效模型配置，首次打开应用即可直接对话
   - 若缺少 API Key，不允许只给模糊报错，必须进入明确配置引导
   - 配置页只保留完成对话所需最小必要项：provider / model / baseUrl / apiKey
   - API Key 保存成功后，无需手工重启整套链路即可开始对话

4. **安装状态和失败原因可表达**
   - 安装阶段失败时要明确告诉用户是哪个安装步骤失败
   - 首启阶段失败时要能区分：网关未启动、模型未配置、配置无效
   - 禁止再出现“网关已启动但实际不可对话”的假成功状态

5. **路径与版本策略固定**
   - 严禁安装阶段回退到在线拉取 Hermes 源码
   - 严禁依赖用户本机 Git / Node 外部环境
   - 安装版与免安装验证版必须使用同一套固定版本 Hermes 资源策略

### 5.3 页面 / 交互结果

- 安装过程中：
  - 若 Hermes 预装仍在进行，安装器内必须有明确进度或步骤提示
  - 不允许把 Hermes 安装问题全部留到用户首次打开应用后再处理
- 首次打开应用后：
  - 能直接进入工作界面
  - 若网关已就绪且模型已配置，可直接对话
  - 若缺少模型 API Key，显示清晰配置引导，而不是离线报错
- 用户配置 API Key 后：
  - 无需手工执行命令
  - 无需理解 Hermes 细节
  - 回到会话页即可正常发送消息

### 5.4 完成标准

必须同时满足：

1. 安装版安装完成后，本地 Hermes 网关运行环境已准备完毕
2. 首次打开 `Ti Work.exe` 时，不再依赖长时间首装 bootstrap 才能进入可用状态
3. 若模型配置已存在，用户首次进入会话页即可直接成功发送一条消息
4. 若模型配置不存在，系统必须明确提示配置 API Key，且配置成功后立即可发送第一条消息
5. 用户全程无需手工执行任何命令
6. 不再出现误导性的“执行引擎未连接”或“网关失败”假报错

### 5.5 安装版实施重点

这一阶段的核心不是继续优化免安装体验，而是把正式安装流程做成真正的产品闭环。

#### A. 安装程序要负责什么

- 选择安装路径
- 写入 Ti Work 应用主体
- 写入 Hermes 固定版本资源
- 完成 Hermes 工作目录初始化
- 生成网关最小配置骨架
- 预置运行所需 token / env / config 骨架
- 完成必要依赖准备与网关可启动性检查

#### B. 首次启动要负责什么

- 检查 Hermes 网关是否可直接启动
- 检查本地模型配置是否完整
- 若缺少 API Key，则进入配置引导，而不是报错
- 若配置完整，则直接进入可对话状态

#### C. 用户体验目标

- 用户理解的是“安装 Ti Work”，而不是“再安装一个 Hermes”
- 用户不需要知道 Hermes 工作目录、bootstrap、manifest、gateway 这些技术概念
- 对用户来说，安装成功的标准就是：打开后能开始对话；若缺 Key，就把 Key 配完后立刻能对话

### 5.6 未完成前禁止推进的内容

- 浏览器自动化主卖点
- 数据库产品化
- 移动端主路径
- 企业能力对外宣发
- 一级菜单继续扩张

## 6. P1：企业办公核心闭环

### 6.1 阶段目标

让 Ti Work 从“能聊天”升级为“能处理员工日常工作”。

P1 解决的是：员工每天打开软件，到底能拿它完成什么具体工作。

### 6.2 本阶段要形成的产品能力

#### A. 工作台

必须形成一个真正的“今日工作入口”页面，至少包含：

- 今日待办
- 最近文件
- 最近会话
- 最近流程
- 工作提醒 / 审批提醒
- 今日工作摘要

用户效果：

- 打开软件第一眼就知道今天要做什么
- 不需要先理解系统结构，再决定去哪个页面

#### B. 会话中心

会话页要从普通对话框升级为“任务发起中心”：

- 支持从文件、流程、网页任务发起会话
- 支持结构化任务上下文
- 支持附件、指令模板、会话标签
- 支持历史回溯

用户效果：

- 会话不只是聊天，而是办公任务的入口

#### C. 执行中心

执行域至少要覆盖四件事：

1. 文件处理
2. 浏览器自动化
3. 终端执行
4. 数据库操作入口（先做基础版）

用户效果：

- 用户不是只能“问 AI”，而是可以让它真正做事

#### D. 流程中心

把离散能力转成可复用流程：

- 任务
- 编排
- 多智能体
- 定时任务
- 流程模板

用户效果：

- 重复工作不再一遍遍重新描述
- 常见工作可以保存成模板

#### E. 知识中心

先形成“个人+团队基础沉淀”：

- 记忆
- 技能
- 用户档案
- 规则 / 纠正项

用户效果：

- 平台开始记住企业和员工怎么工作

#### F. 权限与安全中心（最小版）

必须先给用户一个可视化、可理解、可控制的安全边界，而不是把授权逻辑藏在配置文件或弹窗细节里。

P1 最小版至少要具备：

- 文件系统目录白名单 / 黑名单
- 工具级授权开关（文件、终端、浏览器、数据库、网络、MCP）
- 危险动作二次确认
- 会话级临时授权
- 最近授权记录与最近危险动作提示

用户效果：

- 用户知道智能体当前能做什么、不能做什么
- 用户可以直观看到哪些目录允许访问，哪些目录禁止访问
- 用户在关键操作前有明确确认，而不是事后才发现被执行

### 6.3 P1 交付物

必须至少形成：

- 新一级菜单结构原型
- 工作台页面 v1
- 执行中心页面 v1
- 流程中心页面 v1
- 知识中心页面 v1
- 权限与安全中心 v1
- 工作场景模式中心 v1
- 会话作为任务发起中心的交互收口

### 6.4 P1 完成标准

必须同时满足：

1. 一个普通企业员工无需懂技术，也能看懂主菜单
2. 用户能完成至少 3 类真实办公闭环：
   - 文件整理 / 改写 / 汇总
   - 网页系统查询 / 填报 / 提取
   - 重复工作保存为流程模板
3. 不必在十几个菜单之间来回找功能
4. 用户能清楚配置智能体的授权边界，并理解危险动作何时会被拦截或确认
5. 用户安装后可按岗位初始化工作模式，后续也能随时切换场景而不丢失个人数据与治理边界

### 6.5 P1 不做什么

- 先不追求复杂企业中台
- 先不做极重的数据库治理
- 先不做大规模组织分析能力

### 6.6 工作场景模式切换与菜单自适配机制

Ti Work 作为通用桌面办公智能体，不能假设用户永远只处于一个固定场景。

真实办公里，用户经常会出现：

- 同一个人跨行业职能处理事务
- 同一个岗位在不同时间段切换不同工作模式
- 同一个用户同时存在“通用办公模式”“项目专项模式”“行业专项模式”
- 用户岗位、职责、团队边界发生变化

因此，首启时进行一次岗位初始化是合理的，但产品不能停留在那里，必须支持：

**首次初始化 + 后续随时切换场景 + 系统智能建议切换。**

#### 6.6.1 方案结论

Ti Work 菜单不能写死为单一行业版本，而应采用：

1. **稳定通用骨架**
   - 一级菜单骨架长期稳定

2. **工作模式层**
   - 不同行业 / 岗位 / 项目场景加载不同工作模式

3. **角色裁剪层**
   - 普通员工、主管、管理员看到的菜单范围不同

4. **个人习惯微调层**
   - 用户自己的常用模块、模板、知识源、快捷动作可继续自适配

也就是说：

- 安装包只有一个通用产品壳
- 菜单、首页、默认模板、默认知识源、默认流程通过工作模式动态适配

#### 6.6.2 首次初始化机制

首次打开应用时，系统应提供一个轻量的“工作模式初始化”流程，而不是直接丢给用户一套固定通用菜单。

初始化至少应采集：

1. **行业 / 场景**
   - 通用办公
   - 律所
   - 财务
   - 人事
   - 其他行业

2. **岗位角色**
   - 普通执行角色
   - 助理 / 专员
   - 主管 / 负责人
   - 管理员

3. **高频工作类型**
   - 搜索资料
   - 写文档
   - 处理审批
   - 管理文件
   - 跑固定流程
   - 知识沉淀

初始化完成后，系统应自动决定：

- 一级菜单别名
- 首页卡片
- 默认模板集
- 默认知识源
- 默认流程集
- 默认快捷动作
- 默认权限建议

#### 6.6.3 后续场景切换机制

生产级产品必须支持后续场景切换，而不是只能首装配置一次。

建议支持三种切换层级：

1. **长期默认场景**
   - 用户最常用的主模式
   - 例如：通用办公、律所办案、财务处理

2. **临时场景切换**
   - 某一阶段短期切换
   - 例如：本周临时处理合同审阅或月结任务

3. **任务级场景**
   - 针对当前任务指定模式
   - 例如：这次按“财务月结模式”执行

#### 6.6.4 场景切换后哪些会变化

工作模式切换后，允许变化的包括：

- 菜单名称
- 菜单排序
- 首页卡片内容
- 默认模板
- 默认知识源
- 推荐流程
- 默认快捷动作
- 行业术语表达

这些变化属于“工作视图与默认策略变化”，是合理且必要的。

#### 6.6.5 场景切换后哪些不能被覆盖

场景切换不能破坏用户的基础数据与治理边界。

不应被直接覆盖的包括：

- 用户全局身份信息
- 全局权限与安全底线
- 全局禁区目录
- 核心危险动作规则
- 审计记录
- 历史知识资产

结论上要坚持：

**场景切换是切换工作模式，不是重置用户。**

#### 6.6.6 产品页面与交互方式

必须提供一个明确可见的“工作模式切换器”，而不是依赖隐藏设置。

建议落点如下：

1. **顶栏 / 工作台顶部**
   - 作为当前模式显示与快速切换入口

2. **设置页中的“工作模式”配置页**
   - 查看当前模式
   - 调整行业、岗位、高频工作
   - 恢复默认模式
   - 管理自定义模式

3. **任务发起时的模式选择**
   - 当前任务可临时指定模式

#### 6.6.7 自动建议切换机制

系统应支持“智能建议切换”，但不应擅自自动切换。

例如：

- 你最近连续在处理报销、付款、对账任务，是否切换到“财务处理模式”？
- 你最近连续在检索法规、起草意见书，是否切换到“律所办案模式”？

产品原则应是：

- 系统给出建议
- 用户显式确认
- 记录本次切换来源与是否长期生效

#### 6.6.8 与菜单自适配的关系

菜单适配不应靠为每个行业单独做一套安装包，而是靠“骨架稳定、表达可变”实现。

推荐模型如下：

1. **骨架层**
   - 工作台
   - 业务
   - 文档
   - 知识
   - 协作
   - 管理（按角色显示）

2. **模式映射层**
   - `业务` 可按模式显示为：
     - 办案
     - 财务
     - 人事
     - 通用业务

3. **个人微调层**
   - 常用菜单置顶
   - 隐藏低频模块
   - 收藏快捷动作
   - 首页卡片重排

#### 6.6.9 与个人工作画像的联动

工作模式切换必须和“个人工作画像与习惯学习中心”打通。

至少要支持：

- 不同场景下的偏好隔离
- 不同场景下的模板偏好
- 不同场景下的知识源偏好
- 不同场景下的授权习惯差异

例如：

- 用户在“财务模式”下偏好 Excel 输出
- 用户在“律所模式”下偏好 Markdown 研究纪要
- 用户在“通用办公模式”下更强调审批提醒和任务摘要

#### 6.6.10 商业分层与定价策略

工作场景模式不只是产品体验问题，也直接影响商业模式。

这里必须明确一个原则：

**不要按菜单收费，要按能力包、使用成本和行业价值收费。**

原因很直接：

- 用户不能接受“只是多了一个菜单名字就要额外付费”
- 但用户可以理解“某个行业模式背后附带了更强模板、知识包、流程包和治理能力，因此价格更高”

也就是说：

- `工作场景模式` 是产品机制
- `行业工作包`、`企业治理能力`、`高成本执行能力` 才是主要商业分层点

##### A. 默认开通策略

建议默认开通一个：

- **通用办公模式**

原因：

- 用户安装后必须立刻可用
- 不能因为未购买行业包而卡在初始化阶段
- 通用模式是产品体验入口，也是后续升级行业模式的基础

##### B. 推荐商业分层

建议分为四层：

1. **基础版**
   - 默认通用办公模式
   - 基础工作台
   - 基础文档处理
   - 基础知识沉淀
   - 基础权限与安全能力

2. **专业版**
   - 多工作模式切换
   - 更强个人工作画像
   - 更多模板、流程与知识源接入
   - 更强浏览器 / 文件处理能力

3. **行业工作包**
   - 律所工作包
   - 财务工作包
   - 人事工作包
   - 其它行业包
   - 每个包至少包含：
     - 行业首页
     - 行业模板
     - 行业流程
     - 行业知识源
     - 行业术语表达

4. **企业版**
   - 审批
   - 审计
   - 权限与安全中心高级治理
   - 组织级工作模式下发
   - 多人协作
   - 成本控制与席位管理

##### C. 适合做收费差异的能力

适合拉开价格差异的，不是菜单名称，而是以下能力：

- 行业模板库
- 行业知识包
- 行业流程包
- 深度浏览器自动化
- 大批量文档处理
- OCR / 解析
- Obsidian / 本地知识仓高级联动
- 个人工作画像高级学习能力
- 审批、审计、组织级权限治理

##### D. 不建议做收费门槛的基础能力

以下能力不应被切得太碎，也不适合做成“没有就无法放心使用”的收费门槛：

- 基础工作模式初始化
- 基础场景切换
- 基础权限与安全能力
- 基础危险动作确认
- 基础审计可见性

原因是：

- 没有这些基础能力，用户很难放心把桌面智能体真正用于办公
- 这些应该作为产品可信度的一部分，而不是纯增值障碍

##### E. 价格表达方式

用户应该感知为：

- 我买的是 **Ti Work 通用办公智能体**
- 如果我是律师，我再开 **律所工作包**
- 如果我是财务，我再开 **财务工作包**
- 如果我是企业，我再开 **企业治理版**
- 如果我需要更强自动化或更多额度，再加 **高级执行包 / 用量包**

这样表达比“按菜单收费”清楚得多，也更符合办公软件采购逻辑。

##### F. 产品与商业的一致性原则

最终必须坚持：

1. 通用模式开箱可用
2. 行业模式通过行业工作包体现差异化价值
3. 企业治理能力作为更高层级收费点
4. 高成本执行能力可做额度或高级版收费
5. 不把基础安全能力做成缺失项

#### 6.6.11 云端开通体系、企业管理后台与桌面端登录机制

如果 Ti Work 后续走的是面向行业的 ToB 交付路径，那么工作场景模式、行业工作包、企业成员管理、共创资产沉淀和商业授权都不能只靠本地桌面端完成，必须建立云端体系。

这里必须明确：

**桌面端不是孤立产品，而应是“云端身份与授权体系”下的执行与使用终端。**

也就是说：

- `Ti OPC` 负责统一对外产品入口、注册登录承接、产品展示与开通引导
- `Ti-Work-Web` 负责统一身份能力模块、客户、行业包、席位和版本管理
- 企业管理后台负责成员邀请、成员权限与工作包分配
- 桌面端负责登录、同步授权、缓存资源包和实际办公执行

##### A. 为什么必须有云端体系

如果没有云端体系，以下关键问题无法成立：

1. 无法识别当前桌面端用户属于哪家机构
2. 无法识别该用户是否已购买某个行业工作包
3. 无法实现席位分配、到期控制和企业成员管理
4. 无法判断该客户是否属于行业共创客户
5. 无法把工作包升级、版本发布和行业资源同步给桌面端

因此，对行业化 ToB 路线来说，云端体系不是可选增强，而是产品交付模型的一部分。

##### B. 建议的云端产品形态

建议至少形成三个云端面：

1. **产品官网 / 门户**
   - 展示产品、行业方案、价格策略、联系销售与开通入口
   - 承接客户了解产品、申请试用和正式开通

2. **平台运营后台**
   - 平台侧使用
   - 管理客户、行业工作包、版本、授权、共创客户、资产审核、工作包发布

3. **企业管理后台**
   - 客户侧管理员使用
   - 管理本企业成员、席位、角色、行业包开通状态和邀请关系

说明：

- 首版可以把官网做轻，把“开通与管理后台”做重
- 但不能只做本地桌面端而完全缺失云端开通和身份体系

##### C. 桌面端必须支持登录

如果行业工作包、企业授权、成员席位和共创能力都由云端控制，那么桌面端必须支持登录。

桌面端登录后，至少要同步以下信息：

- 当前用户是谁
- 属于哪家机构 / 哪个租户
- 当前角色是什么
- 是否已开通某个行业工作包
- 是否有共创权限
- 本地应加载哪个工作模式与资源包

因此后续不应再把“完全匿名、不登录即可进入完整办公模式”作为正式交付形态。

这里还必须进一步定清：

**即使未开通行业工作包，也应进入统一云端账号体系。**

也就是说，后续不建议长期保留两条正式产品路径：

- 一条“匿名本地版”
- 一条“云端授权企业版”

这样的双轨模型会带来：

- 菜单与工作模式两套逻辑
- 授权与版本两套逻辑
- 资源包分发两套逻辑
- 商业化升级路径割裂
- 资产沉淀与客户支持链路割裂

因此更合理的正式产品结论是：

**所有正式用户统一登录，区别只在于云端下发的权益层级不同。**

##### D. 统一权益模型的推荐方案

最合理的正式方案不是“行业用户走云端、普通用户走本地”，而是：

**统一云端账号体系 + 默认通用办公版权益 + 行业工作包增量授权 + 本地缓存可用**

这意味着：

1. 所有正式用户都登录
2. 未购买行业工作包的用户，也会获得一个基础权益
3. 该基础权益建议命名为：
   - `个人版` 或
   - `通用办公版`
4. 行业工作包是在基础权益之上追加授权
5. 桌面端根据云端授权决定当前可见菜单、可用能力和默认工作模式

这样做的好处是：

- 升级路径清晰
- 商业模型统一
- 客户支持与问题排查统一
- 工作包分发和版本下发统一
- 后续从个人版升级到律所版 / 财务版不需要换产品形态

##### E. 桌面端如何识别“个人版 / 通用办公版”

桌面端不应通过本地硬编码去猜测当前用户是不是“个人版”。

正确方式应是：

**由云端返回统一授权对象，桌面端仅按照授权对象渲染。**

至少要包含：

- 当前版型
- 当前租户
- 当前可用行业工作包
- 当前功能开关
- 当前共创权限

例如可抽象为：

- `edition`: `personal` / `general_business` / `enterprise`
- `packages`: `general_office` / `law_firm_pack` / `finance_pack`
- `features`: 团队管理、共创、组织治理等能力开关

也就是说：

**桌面端可以识别“当前是个人版”，但这个识别依据必须来自云端授权结果，而不是本地自行推断。**

##### F. 登录方式建议

对 ToB 行业交付场景，不建议把“手机号验证码注册”作为唯一主路径。

更合理的优先级应为：

1. **企业邀请制登录**
   - 企业管理员在后台添加成员并发起邀请
   - 成员通过邀请链接完成账号激活并登录桌面端
   - 这是首选主路径

2. **手机号验证码登录**
   - 可作为辅助登录方式
   - 适合轻量试用、账号找回或后续开放的自助体验场景

3. **企业邮箱 / SSO**
   - 作为后续增强方向
   - 适合规模化企业交付

结论：

**不是必须手机号验证码注册，而是必须有云端身份体系；企业邀请制应优先于纯手机号自助注册。**

##### G. 行业工作包的分发方式

行业工作包不应仅存在于桌面安装包中，而应采用：

**云端授权 + 桌面端下载同步 + 本地缓存运行**

也就是：

1. 用户登录桌面端
2. 桌面端向云端拉取用户可用的行业工作包与工作模式
3. 下载对应资源包或资源包增量
4. 在本地缓存后投入使用
5. 周期性校验授权与更新

这样可以同时满足：

- 商业授权控制
- 多租户隔离
- 版本统一下发
- 桌面端良好的本地使用体验

注意：

- 不建议做成“每次启动都强依赖云端实时取包”
- 也不建议继续走“行业包完全内嵌安装包且不可控更新”的长期方案

##### H. 购买与支付的推荐链路

对 ToB 产品，不建议把完整购买支付主链路放在桌面端里实现。

更合理的是：

1. 官网 / Web 后台完成：
   - 套餐购买
   - 行业工作包开通
   - 席位增购
   - 续费和到期管理

2. 云端更新授权状态

3. 桌面端登录后只负责：
   - 拉取授权状态
   - 同步可用工作包
   - 展示到期提醒与可用权益

也就是说：

**支付在 Web，使用在桌面端。**

##### I. 企业管理后台必须支持的最小能力

企业管理后台首版至少应支持：

- 企业基本资料
- 成员邀请
- 成员角色分配
- 席位分配
- 行业工作包开通状态查看
- 工作模式默认配置
- 共创客户开关与成员可见范围

其中“成员邀请”是关键能力，因为这决定了桌面端登录后是否能识别当前用户的组织归属。

##### J. 与桌面端的最小联动能力

桌面端首版至少需要补齐：

- 登录页 / 激活页
- 当前账号与机构信息展示
- 授权和行业工作包同步
- 本地资源包缓存
- 到期 / 失效提醒
- 当前工作模式来源说明

例如用户应能明确看到：

- 当前属于哪家机构
- 已开通哪个行业工作包
- 当前启用的是哪种工作模式
- 当前是否拥有共创权限

##### K. 最终产品判断

如果 Ti Work 走的是行业化 ToB 交付路径，那么合理形态应该是：

- 云端完成客户开通
- 企业管理员在云端完成成员邀请
- 用户登录桌面端后同步工作包与权限
- 桌面端作为实际办公执行终端

也就是说：

**不是继续强化“完全本地匿名版”，而是统一进入“云端账号 + 基础权益 + 行业包增量授权 + 桌面执行 + 本地缓存”的正式产品形态。**

##### L. 实施顺序判断：应先建设云端 Web 基座

如果接下来要把桌面端正式改造成“登录后同步身份、机构、授权、行业包与工作模式”的产品形态，那么在实施顺序上，应该先建设云端 Web 基座，而不是先做桌面端假登录。

这里的“云端 Web 基座”不是先做一个重营销、重展示的官网，而是优先建设以下三类真实能力：

1. **云端认证与账号中心**
   - 统一账号体系
   - 登录态签发与续期
   - 账号与企业 / 租户关系识别

2. **平台运营后台**
   - 客户开通
   - 行业工作包授权
   - 企业版 / 通用版 / 个人版权益管理
   - 工作包版本发布与资源包下发控制

3. **企业管理后台**
   - 企业管理员登录
   - 成员邀请
   - 成员角色与席位分配
   - 企业默认工作模式配置

在这个判断下，官网主界面可以同步建设，但首版优先级应低于“登录、授权、后台”本身。

也就是说：

**先做云端身份与授权中枢，再做桌面端登录改造，最后再逐步补强营销官网、支付链路和资产中心。**

如果顺序反过来，会出现几个问题：

- 桌面端虽然有登录页，但没有真实授权对象可同步
- 无法判断当前用户属于哪个机构、拥有哪些工作包
- 菜单与工作模式无法根据云端权益真实切换
- 后续还要二次重构桌面端登录与授权链路

因此，桌面端登录改造的前置条件不是“一个漂亮的 Web 页面”，而是：

**一套可用的云端认证、授权、企业与后台管理体系。**

##### M. 当前阶段重新校准后的功能优先级

基于目前已经明确的产品目标，接下来不应平均推进所有模块，而应按“是否直接支撑正式交付闭环”来排序。

###### P0：正式交付前置能力，必须先做

1. **云端认证与统一账号体系**
   - 为桌面端登录提供真实身份来源
   - 统一个人 / 通用办公版 / 行业版 / 企业版的权益识别

2. **平台运营后台**
   - 让平台侧能完成客户开通、授权下发、行业工作包管理与版本控制

3. **企业管理后台**
   - 让客户侧管理员能完成成员邀请、席位配置、角色管理与工作包分配

4. **桌面端登录与授权同步改造**
   - 登录
   - 拉取授权对象
   - 根据云端授权切换菜单、模式、资源包与可见能力

###### P1：进入首发闭环的核心产品能力，应紧随其后

1. **权限与安全中心**
   - 决定用户是否敢把智能体真正用于办公
   - 也是企业采购时非常敏感的能力

2. **统一 Agent 执行事件采集层**
   - 这是后续沉淀共创资产、提炼行业流程和形成平台复用能力的基础

3. **个人工作画像与习惯学习中心**
   - 让桌面端从“能用”走向“熟悉用户工作方式”
   - 但前提是已经有统一账号、权限边界和执行采集能力

4. **行业工作包分发与本地缓存机制**
   - 让云端授权真正能映射为桌面端可用资源

###### P2：增强商业闭环与运营效率，可在首发闭环后补强

1. **官网主界面 / 行业方案页 / 开通引导页**
   - 对外承接销售与试用转化

2. **支付、续费、席位增购链路**
   - 重要，但不一定要在桌面端登录改造前全部完成

3. **行业资产中心 / 共创资产提交流程 / 审核发布后台**
   - 是平台化复制的关键，但要建立在账号、授权、执行采集完成之后

4. **完整版本中心与桌面端自动更新闭环**
   - 提升交付效率与运维能力

###### P3：可后置的优化项

- 官网营销内容深化
- 更细的运营分析看板
- 更复杂的自动化审批流
- 多行业更深度的专属能力包扩展

##### N. 推荐的实际推进顺序

最顺的顺序应是：

1. 云端认证中心
2. 平台运营后台
3. 企业管理后台
4. 桌面端登录与授权同步
5. 权限与安全中心
6. Agent 执行事件采集层
7. 行业工作包分发与缓存
8. 个人工作画像与习惯学习中心
9. 官网与支付链路补齐
10. 行业资产中心与平台复制能力

这个顺序的核心原则是：

**先把“身份、授权、组织、分发、执行边界”打通，再去放大“学习、沉淀、复制、商业化扩张”。**

##### P. 现有项目承接判断与替换策略

基于当前仓库现状，`Ti-Work-Web` 与 `Ti-Work-WebSite` 都不是空白目录，因此不建议简单粗暴地“删掉旧项目后重建”。

更合理的判断是：

###### 1. `Ti-Work-Web`：保留项目承接云端中枢，但要做结构化重构

当前 `Ti-Work-Web` 已经具备以下基础：

- 租户、账号、许可证、席位、审计的后端基础能力
- 桌面端登录、心跳、席位续租接口雏形
- 管理控制台前后端联通雏形
- featureSet / edition / license 的初步商业控制逻辑

因此，它不是“旧垃圾项目”，而是：

**可以继续承接云端中枢开发的基础底座。**

但同时也必须正视当前不足：

- 当前数据模型还缺少邀请、企业成员关系、工作包授权对象、工作模式配置、刷新 token / 设备会话等正式能力
- 当前前端 `web/src/App.tsx` 仍是单文件控制台形态，不适合继续叠加大量正式模块
- 当前后端目录按功能域拆分还不够细，后续继续堆逻辑会很快失控

所以对 `Ti-Work-Web` 的正确策略不是“整仓替换”，而是：

**保留后端与测试基础，重构目录结构，替换当前控制台前端实现。**

###### 2. `Ti-Work-WebSite`：保留为官网项目，不与中枢项目合并

`Ti-Work-WebSite` 当前已经是独立官网项目，适合继续承接：

- 产品官网首页
- 行业方案页
- 下载页
- 联系销售 / 预约演示入口

因此不建议把官网并回 `Ti-Work-Web`。

更合理的做法是：

- `Ti OPC` 负责统一对外产品入口、注册登录承接与产品操作面
- `Ti-Work-Web` 负责统一身份能力模块、后台、授权、企业管理
- `Ti-Work-WebSite` 负责过渡品牌页与对外营销承接，后续可按阶段并入 `Ti OPC`

也就是说：

**两个项目都保留，但职责必须重新拉齐，不能继续边界模糊。**

###### 3. 是否可以“在这两个目录里替换旧项目”

可以，但应区分两种替换：

1. **`Ti-Work-Web`**
   - 可以在原目录内替换当前前端结构
   - 可以在原目录内重构后端模块结构
   - 不建议抹掉现有 server 能力重新开第三套项目

2. **`Ti-Work-WebSite`**
   - 可以在原目录内替换官网页面结构与视觉实现
   - 不建议让它承担登录鉴权与企业后台职责

结论是：

**可以在原目录内做“结构性替换”，但不建议做“项目级推倒重来”。**

##### U. 模型能力接入：账号注册即自动开通云端模型通道，执行端只持访问凭证（决策定稿）

> 决策日期：2026-09-09。本节与 C「桌面端必须支持登录」、D「统一权益模型」同属一套"登录即授权"口径，作为 Ti 系列正式产品获取模型能力的统一依据；对标参照为 ZCode / 智谱"账号授权连接模型"的连接方式。

**决策结论**

正式产品路径下，桌面端获取模型能力的主路径采用 **"账号授权、云端下发凭证"**，不采用"用户自持并手动填写第三方 API Key"作为主路径。

参照 ZCode / 智谱的连接方式：桌面端不落任何第三方明文 Key，账号登录即绑定平台模型通道，额度与套餐判断收口在云端账号体系，本地仅保存可刷新的访问凭证引用。该方式与"支付真相与权益收口在云端、执行端只发起动作"的分层原则一致。

**云端账号创建即默认开通模型通道（Ti 落地口径）**

1. 用户在云端（Ti OPC 统一账号体系）注册、或企业成员被邀请激活时，系统为该账号 **默认自动创建"账号托管模型密钥"**，并同步开通默认权益（个人版 / 通用办公版）对应的模型额度通道。
2. 该密钥由云端账号体系托管持有，对用户不可见、不可导出；上游模型渠道由平台统一对接，用户无需也不被引导去第三方平台自行申请 Key。
3. 桌面端完成账号登录后，由云端授权中心为当前设备签发短期访问凭证；桌面端仅持久化凭证引用，模型请求统一携带凭证经云端鉴权与额度扣减，本地不落明文 Key。
4. 桌面端「设置-模型」在登录态下呈现"通道状态 / 剩余额度 / 默认模型"能力视图，不再把"填写 API Key"作为登录用户的必做引导。

**本地自带 Key 的定位**

「用户自带 API Key」（见 5.5 首启配置引导）仅保留为 **本地单机阶段 / 未登录离线状态**的过渡可用形态，并随云端账号体系落地逐步收敛，不作为正式交付的双轨路径；收敛策略与 D 节"不保留匿名本地版正式路径"保持一致。

**实施阶段判断（推荐窗口）**

推荐将本方式与 **O「首月开发清单」第 4 项「桌面端登录与授权同步改造」同批实施**，而不是提前到本地 P0 单机阶段，也不延后到商业能力完备之后：

- 前置依赖：① 云端认证与账号中心可用（O-1）；② 桌面端登录与授权同步改造完成（O-4）；③ 云端模型中继与额度通道就绪。
- 不宜提前：P0/P1 本地单机阶段云端体系未就绪，若强行要求"登录后才有模型"，会破坏"本地安装即可独立可用"的完成标准，并引入云端强依赖。
- 不宜延后：若先交付登录而未同步下发模型凭证，登录用户仍需手工配置 Key，形成"云端权益 + 本地 Key"两套体系并存的维护成本，与 D 节反对的双轨问题同源。
- 过渡安排：云端账号体系上线前，本地阶段沿用 5.5 的自带 Key 引导；桌面端首次成功登录后，设置-模型页引导切换为"账号已自动开通"，历史已配 Key 仅作为离线降级通道保留。

### 7.5 权限与安全中心生产级方案

权限与安全中心不是一个附属设置页，而是 Ti Work 进入真实办公和企业场景的前置条件。

它要解决的核心问题是：

- 智能体什么时候默认可执行
- 什么时候必须先征得授权
- 哪些目录可以访问，哪些目录必须禁止
- 哪些动作属于危险动作，必须二次确认或审批
- 谁授权了什么、执行了什么、失败了什么，如何追溯

一句话定义：

**权限与安全中心 = Ti Work 的智能体边界控制、风险提示、授权审批与审计留痕的统一中枢。**

#### 7.5.1 产品定位

权限与安全中心要分成两个层次：

1. **设置层的个人权限中心**
   - 面向个人用户和当前工作空间
   - 负责日常授权边界、目录权限、工具开关、危险动作确认

2. **管理层的组织治理中心**
   - 面向企业管理员或团队负责人
   - 负责审批规则、组织级策略、审计回放、高危动作门禁

也就是说：

- `设置` 负责“我允许智能体做什么”
- `管理` 负责“组织允许智能体做到什么程度，以及出了问题如何追溯”

#### 7.5.2 菜单与页面落点

这一能力必须做成可视化菜单，而不是隐藏在配置文件中。

建议菜单落点如下：

1. **设置**
   - 权限与安全
   - 文件系统授权
   - 工具授权
   - 危险动作确认
   - 隐私与数据范围

2. **管理**
   - 审批策略
   - 审计记录
   - 高危动作规则
   - 组织级安全策略

#### 7.5.3 核心边界模型

首版就要明确采用“默认受控、按范围授权、按风险升级确认”的模型。

边界控制至少分四层：

1. **资源范围**
   - 文件系统目录
   - 浏览器网站范围
   - 数据库连接范围
   - 网络访问范围
   - MCP 服务范围

2. **动作类型**
   - 读取
   - 创建
   - 修改
   - 删除
   - 执行
   - 导出
   - 推送 / 发布

3. **风险等级**
   - 低风险：可直接执行或按用户模式处理
   - 中风险：需显式确认
   - 高风险：需二次确认或进入审批

4. **授权时效**
   - 仅当前一步
   - 仅当前任务
   - 仅当前会话
   - 持久策略

#### 7.5.3.1 当前阶段实施补充

为了避免权限中心再次沦为“只可配置、不可执行”的展示层，当前阶段必须先做两件事：

1. **先接文件执行链路**
   - 目录浏览
   - 文件读取
   - 文件写入
   - 重命名
   - 删除
   - 上传
   - 下载

2. **所有命中结果统一事件化**
   - 放行事件
   - 拒绝事件
   - 需确认事件
   - 审批事件

也就是说，权限与安全中心不是纯前端配置中心，而是本地执行链路的第一层门禁。

#### 7.5.4 文件系统权限模型

文件系统是桌面端最敏感、用户最关心的边界之一，必须可视化配置。

至少要支持：

1. **目录白名单**
   - 用户明确允许智能体访问的目录
   - 可针对目录配置不同权限级别

2. **目录黑名单**
   - 明确禁止访问的目录
   - 黑名单优先级高于白名单

3. **目录权限级别**
   - 只读
   - 可创建
   - 可修改
   - 可删除

4. **默认禁区**
   - 系统目录默认禁止访问，如 `C:\Windows`
   - 应用安装目录和系统程序目录默认禁止写入
   - `.git`、`.obsidian`、凭据目录、密钥目录默认禁止写入
   - 用户未授权的盘符或根目录默认不得全盘开放

5. **可视化表达**
   - 目录树选择器
   - 权限标签
   - 风险说明
   - 最近访问记录

#### 7.5.5 工具授权模型

除了文件系统，还必须控制智能体可调用的工具范围。

至少需要支持以下工具分类：

- 文件系统
- 终端
- 浏览器自动化
- 数据库
- 外部网络请求
- MCP 服务
- Git 操作

每类工具都应支持四种授权模式：

- 始终允许
- 每次询问
- 高危时询问
- 始终禁止

#### 7.5.6 危险动作识别与提示

危险动作不能只靠开发者心里有数，必须产品化定义并显式提示。

至少应纳入危险动作的包括：

- 删除文件或目录
- 批量改写文件
- 执行 Shell / PowerShell 命令
- 安装依赖或修改运行环境
- 写入数据库
- 对外网发送敏感内容
- Git 提交、合并、推送
- 修改系统配置或应用配置

每种危险动作至少要支持：

- 风险提示文案
- 执行前确认
- 高危动作二次确认词
- 是否允许加入长期策略

#### 7.5.7 授权交互方式

这块必须可视化，而不是散落在零碎弹窗里。

建议提供三层交互：

1. **全局策略配置**
   - 用户在设置页统一配置默认授权模式

2. **运行时确认面板**
   - 执行前清楚显示：
     - 准备做什么
     - 涉及哪些目录 / 工具 / 网站 / 数据库
     - 风险等级
     - 本次授权作用范围

3. **会话级临时授权**
   - 当前一步允许
   - 当前任务允许
   - 当前会话允许
   - 永久加入规则

#### 7.5.8 审批与组织级治理

当 Ti Work 进入团队或企业环境，光有个人确认还不够，必须支持审批。

P2 生产级版本至少要支持：

1. 高危动作审批
   - 删除共享目录
   - 批量写库
   - 大范围浏览器自动化提交
   - 外发数据

2. 组织级策略下发
   - 管理员统一规定禁区目录
   - 管理员统一规定禁止工具
   - 管理员统一规定高危动作审批门槛

3. 角色差异化策略
   - 普通员工
   - 高级操作者
   - 管理员
   - 审批人

#### 7.5.9 审计与回放要求

权限与安全中心必须与审计中心打通，不然就只有“拦截”，没有“可追责”。

至少要记录：

- 谁发起了动作
- 使用了哪个智能体 / 工具
- 动作发生时间
- 访问了哪些路径 / 网站 / 数据源
- 最终是否执行成功
- 是否经过确认或审批
- 审批人是谁
- 失败原因是什么

高危动作必须支持回放式查看，至少能重建：

- 原始意图
- 授权决策
- 实际执行动作
- 最终结果

#### 7.5.10 分阶段实施方案

##### A. P1 最小可用版

必须完成：

- 权限与安全设置页
- 文件系统白名单 / 黑名单
- 工具级授权开关
- 危险动作确认弹层
- 会话级临时授权
- 最近授权与最近危险动作记录

完成后，普通用户至少能清楚回答：

- 智能体当前能访问哪些目录
- 智能体当前能调用哪些工具
- 哪些动作会先问我
- 哪些动作绝对不允许执行

##### B. P2 生产治理版

必须完成：

- 权限与安全中心 v2
- 审批策略页
- 组织级安全策略
- 高危动作规则中心
- 审计记录与回放
- 角色差异化权限模型

完成后，平台才具备企业可控的安全边界。

#### 7.5.11 验收标准

权限与安全中心完成时，至少要同时满足：

1. 用户无需修改配置文件，即可可视化配置智能体授权边界
2. 用户可明确配置目录白名单 / 黑名单与不同读写级别
3. 用户可明确配置文件、终端、浏览器、数据库、网络、MCP 等工具权限
4. 危险动作在执行前必须有清晰提示，并支持二次确认
5. 用户可进行一步 / 任务 / 会话 / 持久策略四类授权
6. 高危动作具备审计记录，企业场景下可配置审批
7. 普通用户能够理解系统为什么允许、拦截或要求确认某个动作

#### 7.5.12 明确不采用的方案

首版明确不采用以下路线：

- 把权限规则只做成隐藏配置文件
- 智能体默认拥有全盘文件系统写权限
- 高危动作仅靠开发者硬编码，不给用户可见规则
- 只有拦截弹窗，没有授权范围和审计记录

结论：

**权限与安全中心必须作为 Ti Work 的正式产品能力进入设置与管理体系，并以可视化配置、目录边界、工具授权、危险动作确认、审批与审计的组合方式，为智能体建立用户可理解、企业可治理的执行边界。**

### 8.1 阶段目标

让平台不只是“执行工具”，而是开始变成企业知识资产平台。

### 8.2 本阶段要完成的能力

用户效果：

- 新人能快速检索并复用组织经验

要沉淀：

用户效果：

- 经验开始从“人脑中的经验”变成“组织可复用资产”

### 8.3 P3 交付物

- 企业知识中心 v1
- Obsidian 知识仓整合 v1
- 个人工作画像与习惯学习中心 v1
- 岗位 / 员工画像模型 v1
- 团队规则库 v1
- 模板推荐机制 v1

### 8.4 P3 完成标准

必须同时满足：

1. 新人能依赖系统快速找到企业知识
2. 老员工的经验能被结构化沉淀
3. 流程、知识、技能三者开始关联
4. 系统能基于岗位或任务推荐模板 / 知识 / 流程
5. 系统能够逐步学习个人工作习惯，并以可编辑、可审计、可回滚的方式辅助执行

### 8.5 Obsidian 生产级整合方案

Obsidian 不是一个“顺手加一下”的外围能力，而应该被定义为：

**Ti Work 的本地 Markdown 知识仓入口之一，用于承接个人知识、团队知识、项目知识与流程产物沉淀。**

整合目标不是做一个“能打开 Obsidian 文件”的小工具，而是让 Ti Work 能把：

- 会话结果
- 研究结论
- 流程执行产物
- 会议纪要
- SOP / FAQ / 模板
- 员工经验与团队规则

持续沉淀到企业可复用的本地知识仓中。

#### 8.5.1 方案结论

生产级方案不建议一开始就做 Obsidian 插件深绑，也不建议把 Vault 当普通文件夹裸暴露给智能体自由写入。

推荐采用三层路线：

1. **P1：受控接入**
   - 先以“受控本地知识仓”接入 Obsidian Vault
   - 技术上优先走 `MCP Filesystem + Ti Work 内置 Obsidian Skill 抽象`
   - 先解决读、搜、写、归档、模板化写入

2. **P2：治理闭环**
   - 加入审计、目录白名单、敏感目录保护、冲突处理、高危写入确认
   - 让 Vault 写入进入企业可控场景

3. **P3：知识资产化**
   - 把 Obsidian 中的 Markdown 知识与 Ti Work 记忆、流程、规则库、员工画像打通
   - 让它不只是“笔记存放地”，而是企业知识资产的一部分

#### 8.5.2 为什么首版不做插件深绑

首版不建议直接做 Obsidian 插件级深度整合，原因如下：

1. 插件方案更依赖 Obsidian 内部 API、版本兼容与插件生命周期
2. 企业交付时更难做权限边界与安全说明
3. 多 Vault、同步盘、附件目录、模板目录差异会让首版复杂度迅速升高
4. 当前 Ti Work 已具备技能生态与 MCP 扩展能力，先走本地知识仓方案更稳、更快、更容易产品化

因此首版应明确坚持：

- **先接 Vault，不先绑 Obsidian App 内部状态**
- **先把知识沉淀闭环打通，不先追求当前打开笔记、Graph View、Backlinks 实时联动**

#### 8.5.3 目标能力边界

Obsidian 整合首个生产级版本必须至少具备以下能力：

1. 读取指定 Vault 内的 Markdown 笔记
2. 按文件名、路径、标签、Frontmatter、正文关键字搜索
3. 在指定目录下新建笔记、追加内容、更新 Frontmatter
4. 将 Ti Work 会话 / 流程 / 研究结果一键沉淀到 Vault
5. 支持模板化输出，如会议纪要、日报、周报、项目纪要、SOP 草稿
6. 支持附件关联策略，但首版先只做“引用已有附件路径”与“受控写入附件目录”
7. 所有写入必须落在白名单目录，禁止默认全 Vault 任意写

首版暂不承诺：

- 当前 Obsidian 正在打开哪篇笔记的实时感知
- Graph / Backlinks / Canvas 的原生能力映射
- 双向实时监听所有外部变更并即时回刷 UI
- 对第三方 Obsidian 插件生态的深兼容

#### 8.5.4 推荐技术架构

推荐架构分为四层：

**A. 配置层**

- 在 Ti Work 设置中新增“Obsidian / 本地知识仓”配置区
- 用户选择一个或多个 Vault 根目录
- 每个 Vault 需配置：
  - Vault 名称
  - 根目录
  - 默认写入目录，如 `Ti Work/`
  - 模板目录，如 `Templates/`
  - 附件目录，如 `Assets/`
  - 是否允许创建新目录
  - 是否允许覆盖已有文件

**B. 执行层**

- 首版使用受限文件系统访问能力，只允许访问选定 Vault
- 在执行层之上增加 Ti Work 自己的 `Obsidian Skill`
- 该 Skill 不直接暴露任意文件写入，而是提供更高层动作：
  - 搜索笔记
  - 读取笔记
  - 新建笔记
  - 追加到笔记
  - 按模板生成笔记
  - 写入会议纪要 / 研究结论 / 流程总结

**C. 索引层**

- 对选定 Vault 建立轻量索引
- 至少抽取：
  - 路径
  - 文件名
  - 修改时间
  - 标签
  - YAML Frontmatter
  - 标题层级
  - 摘要
- 索引要服务知识搜索、相关推荐、流程沉淀与知识去重

**D. 治理层**

- 所有写入要记录审计日志
- 敏感目录必须支持只读
- 高风险写入必须要求用户确认
- 失败时要保留原因与重试建议

#### 8.5.5 产品页面与交互落点

Obsidian 整合不应做成孤立入口，而应落在现有规划的几个域中：

1. **知识域**
   - 增加“本地知识仓”子页
   - 展示已接入 Vault、目录结构、索引状态、模板、最近沉淀记录

2. **会话域**
   - 在会话结果区提供“沉淀到知识仓”动作
   - 支持选择目标 Vault、目录、模板、标签

3. **流程域**
   - 流程结束后可自动输出执行纪要到 Vault
   - 模板流程可绑定固定知识沉淀目录

4. **管理域**
   - 展示知识仓写入审计、失败记录、敏感目录策略、索引健康状态

#### 8.5.6 生产级权限与安全策略

这一部分必须从第一版就设计进去，否则不能进入企业场景。

必须具备：

1. **目录白名单**
   - 智能体只允许访问用户已授权的 Vault 根目录
   - 默认写入目录为 Vault 下的 `Ti Work/` 或管理员指定目录

2. **读写分级**
   - 目录可配置为只读、可追加、可新建、可覆盖
   - `/Templates`、`/Archive`、`/Rules` 等目录允许单独配置权限

3. **敏感路径保护**
   - 如 `.obsidian/`、插件目录、同步配置目录默认禁止写入
   - 系统配置文件不允许被模型直接修改

4. **写入确认机制**
   - 跨目录写入、覆盖已有文件、批量写入、删除等动作需确认

5. **审计留痕**
   - 谁在什么时候让系统写了什么文件、追加了什么内容、修改了什么 Frontmatter，必须可追溯

#### 8.5.7 知识沉淀数据规范

为了让后续知识检索、模板推荐、流程关联真正可用，Obsidian 输出不能是随意 Markdown，必须有统一规范。

建议 Ti Work 写入 Vault 的文档默认采用统一 Frontmatter：

```yaml
---
title: ""
source: "ti-work"
vault: ""
created_by: ""
created_at: ""
workspace: ""
session_id: ""
flow_id: ""
knowledge_type: ""
tags: []
status: "draft"
---
```

首版至少统一以下 `knowledge_type`：

- `meeting_note`
- `research_note`
- `process_summary`
- `sop_draft`
- `daily_report`
- `weekly_report`
- `faq_draft`

#### 8.5.8 与 Ti Work 其它能力的联动方式

Obsidian 整合不能独立存在，必须与现有主线联动：

1. **与会话联动**
   - 会话可将回答、总结、审批结果沉淀为 Markdown

2. **与流程联动**
   - 流程模板可约定输出目录与输出模板

3. **与记忆联动**
   - 高频引用的笔记可转为长期记忆条目
   - 关键记忆也可导出为知识仓文档

4. **与技能联动**
   - 不同岗位技能可绑定不同知识模板

5. **与审计联动**
   - 知识仓所有写入必须进入管理域审计记录

#### 8.5.9 分阶段实施方案

##### A. P1 最小生产版

必须完成：

- 单 Vault 接入
- Vault 路径选择与检测
- 知识仓搜索
- 受控目录写入
- Markdown 模板输出
- 会话结果一键沉淀

完成后用户至少能做到：

- 让 Ti Work 把研究结果写入 Obsidian
- 让 Ti Work 把会议纪要写入 Obsidian
- 让 Ti Work 把重复工作的输出按模板沉淀到 Obsidian

##### B. P2 企业可控版

必须完成：

- 多 Vault 管理
- 目录权限模型
- 敏感路径保护
- 写入审计与失败回放
- 批量写入确认
- 索引重建与健康检查

完成后平台才可以进入企业团队级共享知识场景。

##### C. P3 资产化版本

必须完成：

- Vault 文档与企业知识中心双向关联
- 基于岗位 / 任务 / 流程推荐相关笔记
- SOP / FAQ / 模板从笔记中抽取结构化资产
- 规则库与知识仓关联

完成后 Obsidian 不再只是知识载体，而成为企业知识资产体系的一部分。

#### 8.5.10 验收标准

Obsidian 整合生产级方案完成时，至少要同时满足：

1. 用户可在设置中完成 Vault 接入，无需手工命令配置
2. 智能体只能访问被授权的 Vault 与目录
3. 会话 / 流程结果可稳定沉淀为 Markdown 文档
4. 写入内容具备统一 Frontmatter 与模板结构
5. 敏感路径默认受保护，不能被模型任意改写
6. 所有写入、覆盖、失败都有审计记录
7. 普通员工无需理解 Obsidian 技术细节，也能完成知识沉淀闭环

#### 8.5.11 明确不采用的首版路线

为避免方案发散，首版明确不采用以下路线作为主实现：

- 直接把整个 Vault 作为任意文件系统暴露给模型
- 先做 Obsidian 插件再反向补 Ti Work
- 依赖用户自行安装并配置多个外部脚本后才可使用
- 无模板、无权限、无审计的自由写入方案

结论：

**Ti Work 对 Obsidian 的正确整合方式，不是“再加一个笔记入口”，而是把 Obsidian Vault 作为企业知识沉淀的本地知识仓之一，以受控目录、统一模板、审计留痕和流程联动的方式纳入知识中心体系。**

#### 8.5.12 Ti Work Agent Kernel（统一智能体内核）生产级架构

这一章不是新增一个“技术名词”，而是正式确认 Ti Work 后续所有桌面端、Web 端、行业工作包、权限治理、资产分发与个人画像能力，都必须建立在同一套统一智能体内核之上。

如果没有这层内核，项目后续很容易退化为：

- 功能页面越堆越多，但能力边界越来越散
- 行业包只是页面差异，而不是可复用能力包
- 权限、安全、审计只能分散写在各个模块里
- 企业版、个人版、行业版之间难以保持统一执行语义

因此这里正式定义：

**Ti Work 的目标不是做“很多 AI 页面”，而是做“一个统一智能体内核 + 多种业务壳层 + 多类可控扩展能力”的产品体系。**

##### 8.5.12.1 内核定位

Ti Work Agent Kernel 是 Ti Work 的统一执行与治理中枢，负责把模型、工具、流程、权限、工作区、身份、事件与扩展能力收束到同一套运行语义中。

它不是某一个页面，也不是某一个 Agent 角色，而是所有上层能力共同依赖的基础运行层。

以后无论是：

- 桌面办公助手
- Web 管理后台
- 律所行业工作包
- 财务行业工作包
- 企业级安全与授权体系
- 资产中心与后续行业复制能力

都必须优先接入这层内核，而不是各自发明一套执行机制。

##### 8.5.12.2 五条正式架构基线

以下五条，从本章起正式作为 Ti Work 的项目架构基线。

**1. 统一智能体运行时基线**

- 所有对话、任务、流程、自动化执行、行业能力调用，都必须经过统一运行时
- 运行时统一负责：
  - 会话生命周期
  - 工具调用
  - 任务状态
  - 执行上下文
  - 事件输出
  - 失败重试与中断恢复
- 前端页面不允许直接绕过内核拼装执行逻辑
- 行业工作包也不允许各自维护私有执行闭环

这意味着后续的桌面端、Web 端、行业版都只是入口和视图，不是执行真相来源。

**2. 统一扩展协议基线**

- 插件、技能、工具包、频道接入、行业工作包，统一纳入扩展协议
- 扩展协议至少必须包含：
  - 资产唯一标识
  - 类型定义（技能 / 插件 / 频道 / 行业包 / 模板包）
  - 版本号
  - 兼容的内核版本范围
  - 权限声明
  - 生命周期钩子
  - 安装 / 升级 / 卸载机制
  - 来源、许可证与签名信息
- 不允许继续把“行业能力”做成散落在页面和脚本里的硬编码集合

这条基线的核心目的，是让 Ti Work 后续可以形成真正的平台资产中心，而不是一次性功能堆叠。

**3. 统一身份、工作区与权限边界基线**

- 内核必须天然理解“谁在执行、代表哪个组织、拥有哪些权益、可访问哪些资源”
- 身份与边界至少要覆盖：
  - 当前用户
  - 当前租户 / 企业
  - 当前授权对象
  - 当前工作模式
  - 当前行业包与可用能力
  - 当前工作区与目录白名单
  - 当前危险动作审批状态
- 权限判断必须优先在内核层完成，页面层只负责展示与引导
- 任何写文件、调系统命令、访问敏感目录、调用外部服务的动作，都不能只靠页面提示控制

这条基线决定了 Ti Work 后续是否真的具备企业可治理能力。

**4. 统一持续执行与多入口触发基线**

- Ti Work 不能把智能体定义为“发一条消息，回一条结果”的单轮交互工具
- 内核必须原生支持：
  - 后台常驻执行
  - 定时任务
  - 事件驱动执行
  - 多端触发
  - 中断 / 恢复 / 重试
  - 执行状态回传
- 聊天、流程、定时任务、行业动作、审批流，本质上都属于同一执行体系的不同入口

这条基线决定 Ti Work 是否只是聊天工具，还是可持续工作的办公执行系统。

**5. 统一交付、自检、自愈与升级基线**

- 内核必须包含可交付能力，而不是把安装与运行完全交给用户手工维护
- 交付层至少要具备：
  - 首装向导
  - 运行时检测
  - 依赖缺失诊断
  - 启动失败修复提示
  - bundled runtime 兜底
  - 自动更新与版本兼容检查
- 桌面端、Web 管理端、行业工作包都要受同一套版本兼容规则约束

这条基线直接关系到产品是否能稳定交付到企业真实环境。

##### 8.5.12.3 推荐的统一内核分层

为了避免后续实现中再次把“页面能力”误当“架构能力”，Ti Work Agent Kernel 推荐拆为五层：

**A. Kernel Runtime 层**

- 统一会话
- 统一任务
- 统一工具执行
- 统一事件流
- 统一中断 / 重试 / 恢复

**B. Kernel Governance 层**

- 身份识别
- 租户与授权对象识别
- 权限与安全中心
- 工作区与目录边界
- 审批与审计

**C. Kernel Extension 层**

- 插件 / 技能 / 频道 / 行业包统一注册
- 资产安装、升级、卸载、兼容检查
- 来源、许可证、签名、发布渠道管理

**D. Kernel Delivery 层**

- 首装向导
- 运行时检测
- 启动修复
- bundled runtime
- 版本兼容与升级

**E. Shell / Product 层**

- 桌面端 UI
- Web 管理后台
- 行业方案壳层
- 企业视图与个人视图

只有最上面这一层允许做行业化表达与差异化页面，其余层都应尽可能保持统一。

##### 8.5.12.4 对当前项目的直接约束

从这一章开始，当前项目后续实施时必须遵守以下约束：

1. 新增行业能力时，优先判断是否应作为“行业工作包 / 扩展能力”进入统一协议，而不是先做页面逻辑
2. 新增权限能力时，优先落在权限与安全中心或内核治理层，不允许只在按钮点击处做拦截
3. 新增自动化能力时，优先接入统一任务 / 执行事件体系，不允许另起一套执行状态模型
4. 新增企业能力时，优先通过统一身份、租户、权益语义驱动，不允许靠页面条件散落判断
5. 新增安装、更新、运行时处理逻辑时，优先复用统一交付层，不允许每个模块各自做兜底

##### 8.5.12.5 与后续规划项的关系

这章不是独立能力，而是后续多个模块的共同前置架构：

- 权限与安全中心：依赖统一身份、边界和治理语义
- Agent 执行事件采集层：依赖统一运行时与统一事件流
- 行业工作包分发与缓存：依赖统一扩展协议与统一交付层
- 个人工作画像与习惯学习中心：依赖统一身份、统一执行上下文与统一审计数据
- 云端资产中心：依赖统一扩展协议、兼容规则与来源治理
- 企业版授权体系：依赖统一身份、租户与权益模型

因此，后续任何一个模块如果与这一章冲突，应优先以本章定义的内核基线为准，再调整页面设计与实现方式。

##### 8.5.12.6 最终架构判断

Ti Work 后续不应继续演变为“功能页越来越多的 AI 应用”，而应明确演变为：

**统一智能体内核 + 可治理执行体系 + 可分发扩展协议 + 多行业业务壳层 + 企业级交付能力**

这才是后续能够同时支撑：

- 个人办公
- 企业管理
- 行业工作包
- 云端资产分发
- 权限治理
- 平台复制

的正确长期架构路线。

##### 8.5.12.7 基于 Ti OPC 与 LingShu 现有源码的统一数字员工整合方案

这一节不是概念推演，而是基于当前 `Ti OPC` 与 `LingShu` 代码现状做出的正式架构判断，用来回答一个核心问题：

**Ti OPC 已经在做数字员工与工具编排，LingShu 已经在做画布智能体编排，两边如何避免演变为两套互相割裂的数字员工体系。**

###### 最新口径（以本轮为准）

在后续产品定位上，需要进一步收敛为：

- `Ti OPC`：统一对外产品入口，承接官网、注册登录、工具入口、模板员工入口、数字员工产品操作面
- `LingShu / Ti Agent`：对内能力中枢，不直接面向用户开放
- `Ti Work` 桌面端：执行增强层，补足 `Ti OPC` 不具备的文件操作、浏览器自动化、本地办公执行、习惯沉淀
- `Ti-Work-Web`：统一身份能力模块 + 平台后台 + 企业后台
- `Ti-Work-WebSite`：如继续保留，只作为过渡品牌页；后续可并入 `Ti OPC`

也就是说，后续用户真正感知到的产品应优先收口为：

**`Ti OPC + Ti Work` 桌面端**

而 `LingShu / Ti Agent` 作为内部通用智能体能力中枢，为 `Ti OPC` 数字员工和桌面端数字员工提供补充能力。

先给结论：

**不允许 Ti OPC 与 LingShu 长期并存为两套数字员工内核。**

正式架构决策应为：

- `LingShu` 作为唯一数字员工运行内核
- `Ti OPC` 作为统一对外入口、产品层、工具资产层与场景化入口层
- `Ti Work` 桌面端作为本地执行层、习惯沉淀层与授权受控入口
- `Ti-Work-Web / IAM` 作为统一身份真相来源与后台承载模块

也就是说，后续所有数字员工实例最终都要能归并到同一套运行真相中，而不是分别挂在 `Ti OPC`、`LingShu`、桌面端三处。

###### A. 基于源码的现状判断

当前两边代码已经非常明确地表现出不同定位。

**1. Ti OPC 的数字员工，本质上已经是产品层对象**

从现有代码看，`Ti OPC` 已经具备：

- 用户级数字员工档案 `UserDigitalEmployeeProfile`
- 用户级工作流定义 `AgentWorkflowDefinition`
- 工作流运行、取消、重试、调度、MCP 下发
- 平台数字员工目录、模板复制、自定义员工
- 工具箱配置、能力映射、消费计费、媒体与文本工具调用

但它当前的核心特征是：

- 以 `userId` 为主，而不是以统一租户运行语义为主
- 工具主要注册在 `Ti OPC` 内部
- 会话数字员工仍然保留明显的 Prompt 协议层工具调用痕迹
- 账号体系仍是 `Ti OPC` 自有 `auth:session` 会话

这意味着：

**Ti OPC 当前更像“数字员工产品壳层 + OPC 自有工具能力域”，而不是最适合做唯一运行内核的系统。**

**2. LingShu 的 Agent / Workflow / Skill / KB，更接近中台级唯一内核**

从现有代码看，`LingShu` 已经具备：

- 租户化 `Agent`
- 租户化 / scope 化 `Workflow`
- 租户化 `Skill`
- 知识库、RAG、Milvus 检索链路
- MCP 对外暴露
- 发布后经 `Agent -> Workflow` 的标准运行链路
- OIDC / SSO 接入能力

尤其关键的是，`LingShu` 已经天然具备“发布后的统一运行语义”：

- 画布工作流保存、发布、调试、运行在同一主线上
- MCP 对外暴露的是标准化 `agent_{id}` 能力入口
- Agent 调用最终会落到已发布 workflow 的运行链路上

这意味着：

**LingShu 当前更像“唯一运行时 + 能力编排中台 + 多租户执行真相”。**

###### B. 正式职责边界

基于以上源码事实，后续三端职责必须正式收口为：

**1. LingShu：唯一运行真相**

LingShu 负责：

- Agent 真正实例
- Workflow 真正定义与发布版本
- Skill 真正注册
- KB / RAG / MCP 真正运行接入
- Run trace、执行状态、编排运行语义
- 多租户、scope、版本化发布

以后无论入口来自：

- Ti OPC
- Ti Work 桌面端
- App
- Web 管理后台

只要是“数字员工在真正运行”，最终都必须归到 LingShu 的运行时语义中。

**2. Ti OPC：产品层与工具资产层**

Ti OPC 负责：

- 面向用户的数字员工目录与行业化产品表达
- 平台模板员工、场景化员工市场、购买与开通入口
- OPC 自有工具域的配置、定价、展示、运营
- 简化编排入口与任务编排体验
- 工具能力的商品化、场景化、行业化封装

但 Ti OPC 不应继续承担长期的“唯一编排内核”职责。

换句话说：

**Ti OPC 负责决定“卖什么、给谁用、长什么样、如何组合成产品”，不负责长期维护另一套与 LingShu 平行的底层执行真相。**

**3. Ti Work 桌面端：执行层与习惯沉淀层**

桌面端负责：

- 文件系统、本地应用、浏览器、办公软件等本地执行
- 用户授权边界确认
- 本地事件采集与审计
- 用户习惯、工作偏好、常用流程、操作轨迹沉淀
- 把用户的日常办公行为转化为可学习、可复用的数字员工素材

桌面端不应继续长出第三套独立数字员工对象。

桌面端产生的数据，最终必须沉淀回统一账号下的数字员工画像、记忆、偏好与能力学习体系。

###### C. 四类“真相来源”必须统一定义

为了避免后续又出现“这边一套、那边一套”的情况，后续实施时必须明确四类真相来源：

**1. 身份真相：IAM / SSO**

- 用户身份
- 企业 / 租户归属
- 成员关系
- 席位与权益
- 应用间登录态

都必须统一来自 IAM / SSO，而不是由 `Ti OPC`、`LingShu`、桌面端各自维护主身份。

**2. 运行真相：LingShu**

- 哪个数字员工在运行
- 运行的是哪个发布版本
- 调了哪些 Skill / KB / MCP 工具
- 运行轨迹、成功失败、中断恢复

都以 LingShu 为准。

**3. 工具资产真相：Ti OPC 主导，LingShu 承接运行注册**

考虑到当前“工具全部在 OPC 上”的现状，短中期内不应粗暴要求把所有工具立刻重写到 LingShu。

更合理的做法是：

- 工具定义、商品化信息、场景封装先保留在 Ti OPC
- Ti OPC 增加统一 `Tool Gateway / Skill Gateway`
- 通过标准 contract 同步注册到 LingShu 的 Skill / MCP External Tool
- LingShu 在运行时消费的是标准化工具能力，而不是再次各自手写一套工具

**4. 习惯与画像真相：Ti Work + 云端记忆层联合沉淀**

- 用户操作习惯
- 授权偏好
- 常用目录与工作区
- 常用工具与执行顺序
- 行业协作经验

可以由桌面端采集，但不能只留在桌面端本地。

后续要逐步沉淀到统一账号下的数字员工画像与记忆中心中。

###### D. 为什么不能选择“两套内核并存”

如果继续让 `Ti OPC` 和 `LingShu` 都各自发展完整数字员工体系，后续必然会出现以下问题：

**1. 同一用户会拥有两份数字员工定义**

- 一份在 `Ti OPC`
- 一份在 `LingShu`

久而久之就会无法判断：

- 哪边才是正式版本
- 哪边才是最新工作流
- 哪边沉淀了真实习惯

**2. 同一工具会维护两套接入方式**

- `Ti OPC` 一套工具定义与编排协议
- `LingShu` 一套 Skill / MCP / Canvas 接入

这样后续每增加一个行业工具，都会变成双倍维护成本。

**3. 桌面端会失去统一归宿**

桌面端沉淀出来的用户习惯、授权偏好和工作轨迹，如果无法明确归属到统一数字员工内核，就会在架构上失焦。

**4. 后续 SSO 接入会变成“统一登录，不统一系统”**

这是一种很危险的伪统一：

- 用户看起来只登录一次
- 但底层仍然是两套数字员工世界

这会让后面的权限、安全、资产沉淀、商业复制全部变复杂。

因此这里明确禁止：

**只做表面 SSO，不做数字员工运行真相统一。**

###### E. 生产级整合路线：不是推翻重做，而是一主一从收编

正确路线不是：

- 推翻 Ti OPC 的数字员工产品层重做
- 也不是让 LingShu 全量复制 Ti OPC 页面与产品逻辑

正确路线是：

**一主一从整合。**

其中：

- `LingShu` 为主内核
- `Ti OPC` 为主产品层

也就是：

**产品壳层保留在 Ti OPC，运行内核收口到 LingShu。**

###### F. 正式实施分期

为了满足最小改动原则，推荐按以下阶段推进。

**Phase 1：统一身份映射，不先碰大规模能力迁移**

先建立统一身份层与映射关系：

- `iam_user_id`
- `tenant_id`
- `opc_user_id`
- `lingshu_user_id`
- `desktop_device_id`

这一阶段的目标不是立刻替换所有登录逻辑，而是先完成：

- 账号可映射
- 企业 / 租户关系可映射
- 后续数字员工归并有统一身份基础

在顺序上应优先让 `LingShu` 接入 OIDC / SSO，再逐步改造 `Ti OPC`。

原因很明确：

- `LingShu` 已经具备 OIDC 引导与启动注入能力
- `Ti OPC` 仍然是自有 session 体系

因此从工程成本上，LingShu 更适合作为第一批标准受信方。

**Phase 2：把 Ti OPC 工具能力标准化输出，而不是先迁走页面**

当前所有工具都在 `Ti OPC`，因此第二阶段不应直接要求“把工具迁库”。

应新增一层：

**OPC Tool Gateway / OPC Skill Gateway**

这层统一输出：

- toolCode
- toolName
- inputSchema
- outputSchema
- capabilityCode
- executionMode
- externalActionPolicy
- modelRequirements
- pricing / entitlement metadata

然后把这些能力同步注册为：

- LingShu Skill
- 或 LingShu MCP External Tool

这样做的好处是：

- 工具资产仍可由 Ti OPC 管理
- LingShu 不需要手工重复造所有工具
- 运行时能直接消费标准化能力

在这一阶段，`LingShu` 画布侧也需要同步进入工具节点可视化改造。

这意味着后续不应只停留在“工具已注册”，而要进一步支持：

- `OPC` 同步注册工具在 `LingShu` 画布左侧节点区可见
- 工具以统一 `TOOL` 节点模型进入画布，而不是实现一套 `OPC` 特殊节点协议
- 工具节点可拖拽到画布中参与编排
- 节点自动携带 `inputSchema`、`outputSchema`、`sourceType`、`authPolicy`、`externalActionPolicy`、`billingPolicy`
- 用户在画布中可以像组合其他节点一样组合工具节点

这里正式补充一个交互与实现要求：

**工具节点连线吸附能力必须作为 LingShu 画布工具节点编排的基础体验能力纳入首版方案。**

原因很明确：

- 如果 `OPC` 工具未来要大规模进入 `LingShu` 画布，节点数量会明显增多
- 没有连线吸附，编排体验会变得吃力，尤其在复杂行业流程下会迅速劣化
- 这不是锦上添花，而是影响画布是否具备生产级可用性的基础交互

首版至少要包含以下能力：

**1. 端口吸附**

- 用户拖拽连线接近节点输入 / 输出端口时自动吸附
- 不要求用户必须精确点中很小的端口圆点

**2. 最近可连接端口高亮**

- 当连线拖拽接近合法端口时，高亮提示当前即将连接的端口
- 非法端口不给高亮，避免误导用户

**3. 合法性吸附**

- 只吸附到类型兼容的端口
- 例如文本输出只吸附到文本输入，结构化输出只吸附到兼容 schema 的输入
- 不允许为了“吸附成功”而绕过节点类型规则

**4. 自动校正连线落点**

- 当用户把线放在节点边缘附近时，系统自动修正到最近合法端口
- 这样能显著降低复杂编排时的操作成本

**5. 连线完成后的路径整理**

- 连线建立后自动进行基础路径整理
- 避免工具节点增多后连线过于凌乱，降低可读性

在实现原则上，这里明确要求：

- 连线吸附是 `LingShu` 画布层的统一基础能力
- 不应只给 `OPC` 工具节点单独实现
- 后续 `LLM`、`Agent`、`KB`、`MCP`、审批、条件等节点都应复用同一套吸附机制

也就是说：

**首版可以因 `OPC` 工具进入画布而推动实现，但最终必须沉淀为 LingShu 全局画布交互能力，而不是一次性的工具节点特例。**

**Phase 3：把 Ti OPC 的数字员工实例投影为 LingShu Agent / Workflow**

这一阶段开始处理真正的“数字员工统一”问题。

建议新增：

**Digital Employee Projection Service**

负责把 `Ti OPC` 中的：

- 平台模板员工
- 用户复制员工
- 用户工作流定义
- 启用工具列表
- 模型绑定与外部动作策略

映射到 `LingShu` 中的：

- Agent
- Workflow
- Skill binding
- KB binding
- Published version

注意：

- `Ti OPC` 中的对象短期内可以保留
- 但它们逐步退化为“产品配置稿 / 场景化视图 / 投影来源”
- 真正执行时，以 LingShu 的投影结果为准

**Phase 4：桌面端沉淀统一进入数字员工画像与记忆层**

桌面端后续所有真实办公沉淀：

- 本地执行记录
- 失败修正
- 常用目录与授权
- 常用搜索路径
- 常见输入模板
- 用户风格偏好

都不应只保存在桌面端本地或 OPC 私有表里。

应逐步接入：

- 数字员工记忆层
- 画像演进层
- 长期习惯学习层

让桌面端真正成为“养成入口”，而不是“另一套独立智能体”。

###### G. 同一内核下的三级数字员工资产模型

为了避免后续再次把“平台数字员工”和“用户自己训练出来的数字员工”理解成两套系统，这里正式补充数字员工资产分层模型。

核心原则是：

**平台数字员工、企业专属数字员工、用户专属数字员工，必须运行在同一套内核上，只是资产归属、可见范围、可复制范围不同。**

后续统一采用以下三级模型：

**1. 平台数字员工**

这是平台级资产，负责沉淀已经被验证可复用的行业能力与岗位能力。

其典型来源包括：

- 平台直接设计的模板员工
- 某行业最佳实践沉淀后的标准员工
- 从客户案例中抽象、脱敏、模板化后的公共能力包

平台数字员工的典型特征：

- 归属平台
- 可面向多个企业或多个用户复用
- 必须经过平台审核、脱敏、标准化整理
- 可以作为行业包、岗位包、模板市场的一部分对外提供

可以把它理解为：

**平台模板 / 平台商品 / 平台可复制资产。**

**2. 企业专属数字员工**

这是企业级私有资产，负责承载某家企业自己的 SOP、权限边界、内部知识与协作方式。

其典型来源包括：

- 企业在平台模板基础上的定制化改造
- 企业管理员配置的组织流程、角色职责与内部规则
- 企业侧上传的私有知识库、制度、项目模板、审批要求

企业专属数字员工的典型特征：

- 归属某个企业 / 租户
- 可以在该企业内部多个成员之间共享
- 默认不能跨企业复用
- 平台若想吸收为公共资产，必须经过企业授权、脱敏和二次抽象

可以把它理解为：

**企业内部可复用员工 / 企业私有数字资产。**

**3. 用户专属数字员工**

这是个人级私有资产，负责沉淀某个用户自己的工作习惯、表达风格、常用流程和授权偏好。

其典型来源包括：

- 用户日常使用桌面端的真实办公轨迹
- 用户不断修正后的任务处理偏好
- 用户常用目录、常用工具、常用执行顺序
- 用户个人风格、常见输入模板、常用判断方式

用户专属数字员工的典型特征：

- 归属某个具体用户
- 默认只对本人可见或在本人授权范围内可见
- 更强调“像我自己”，而不是“通用于所有人”
- 默认不能直接上升为平台公共资产

可以把它理解为：

**用户实例 / 个人进化体 / 数字分身雏形。**

##### 三级资产之间的关系

三者关系不应是互相割裂，而应是逐层进化：

1. 平台先提供平台数字员工作为基础模板
2. 企业在平台模板上叠加自己的企业规则，形成企业专属数字员工
3. 用户在企业或平台模板基础上持续使用，逐步形成用户专属数字员工
4. 如果某个企业或用户沉淀出来的模式足够稳定且具有行业复制价值，平台可以在获得授权后进行脱敏、抽象和模板化
5. 完成治理后，才能反向升级为新的平台数字员工

也就是说，正确关系不是：

- 平台一套员工
- 用户一套员工
- 各自独立运行

而是：

**同一内核运行，不同归属层级管理，并允许在治理后向上沉淀为更高层级资产。**

##### 对当前架构的直接含义

这一定义落到当前项目中，意味着：

- `LingShu` 统一承载三类数字员工的运行时
- `Ti OPC` 主要承载平台数字员工的产品化表达、模板化分发与工具资产封装
- 企业后台后续需要承载企业专属数字员工的配置、可见范围和成员共享边界
- `Ti Work` 桌面端后续主要负责沉淀用户专属数字员工的习惯、偏好和本地执行经验

因此后续严禁把“用户自己训练的数字员工”再实现成独立于统一内核之外的另一套系统。

###### H. 对后续开发的直接约束

从这一节起，后续所有数字员工相关开发必须遵守以下约束：

**1. 不允许新增第三套数字员工对象体系**

尤其禁止：

- 桌面端独立定义完整数字员工主档
- App 端再长出一套独立员工
- Web 后台直接绕开统一内核维护私有运行链路

**2. 不允许新增只存在于 Ti OPC、却无法被 LingShu 理解的核心工具能力**

以后新增核心工具时，必须同步考虑：

- 它的标准化输入输出 contract
- 是否可注册为 Skill / MCP External Tool
- 是否可纳入统一运行内核

如果不能，就不能继续当作长期主能力堆在产品层。

**3. 不允许把 SSO 仅当作登录页统一**

统一账号的目标不是“用户少输一次密码”，而是：

- 统一身份
- 统一租户
- 统一权益
- 统一数字员工归属
- 统一审计与资产沉淀

**4. 不允许让 Ti OPC 和 LingShu 同时各自维护“正式发布工作流”**

后续允许存在：

- 产品层草稿
- 简化编排草稿
- 模板配置稿

但正式运行发布语义必须逐步收口到 LingShu。

###### I. 本方案对业务与商业化的直接价值

这套整合路线不仅是技术统一，更直接关系商业复制能力。

一旦统一完成，平台才能真正形成：

- 某行业第一家客户跑出来的优秀数字员工成果
- 经过平台整理、脱敏、模板化后的能力包
- 在后续同类企业中快速复制

否则：

- 工具在 OPC
- 编排在 LingShu
- 习惯在桌面端
- 账号又各自分散

平台就无法形成真正可复制的行业资产中心。

因此，本节正式确认：

**Ti Work 生态中的数字员工统一路线，不是“三套系统互相兼容”，而是“统一身份 + LingShu 唯一运行内核 + Ti OPC 产品层与工具资产层 + 桌面端执行与习惯沉淀层”的一体化架构。**

##### 8.5.12.8 桌面端最终能力边界与左侧菜单收口

随着最新产品边界确定为：

- `Ti OPC` 统一承接对外产品入口、统一登录、平台后台、企业后台、品牌官网与统计资产中心
- `Ti Agent` 只作为对内通用智能体内核
- `Ti Work` 桌面端只作为执行增强层、授权治理层、习惯沉淀层

桌面端前台就不能继续承载“云端后台式”的一级菜单，也不能继续把开发者和运维视角的页面暴露给普通用户。

桌面端必须正式收口为：

**执行增强端，不是云端后台，不是知识中心，不是平台管理台。**

###### A. 桌面端最终能力边界

桌面端后续只保留并强化以下能力：

1. **统一登录与权益同步**

   - 浏览器自动化
   - 本地办公软件协作

   - 本地工作区与素材处理

4. **授权治理**
   - 目录白名单 / 黑名单

   - 支持 `立即开通 / 联系管理员 / 稍后处理`

   - 支付成功后自动刷新权益和可用能力

底部固定入口只保留 2 个：

- 技能、MCP、提供方、系统状态：只保留在设置或专业模式内

###### E. 实施约束

从本节起，桌面端相关开发必须遵守以下约束：

1. 不再新增新的桌面端一级菜单
2. 不再把云端后台能力放进桌面端一级导航
3. 不再把文件、审计、MCP、技能单独抬成前台一级菜单
4. 普通用户打开桌面端后，首先看到的必须是“今天要做什么”和“现在能执行什么”

### 8.6 个人工作画像与习惯学习中心生产级方案

Ti Work 如果要成为“日常熟悉我工作流程”的桌面智能体，不能只停留在开启记忆、保存几条偏好或手工写修正项。

生产级目标应该是：

**让系统以受控、可解释、可编辑、可治理的方式，逐步学习个人的工作目标、常做流程、输出偏好、授权习惯与高频操作模式，并持续提升协作效率。**

这件事本质上不是“训练模型参数”，而是建立一套围绕个人工作的：

- 画像模型
- 习惯学习
- 流程沉淀
- 偏好推荐
- 授权习惯
- 记忆治理

的产品化闭环。

#### 8.6.1 方案结论

当前路线不应走“私有微调模型先行”，而应优先采用：

1. **工作画像 + 长短期记忆**
   - 记录用户稳定偏好、角色、工作域、目录习惯、常用模板、常见规则

2. **历史会话与执行轨迹提炼**
   - 从对话、文件操作、流程执行、审批习惯中提取高频模式

3. **流程模板化与可复用**
   - 把重复工作升级为模板、流程和推荐动作

4. **可视化治理**
   - 所有学习结果可查看、可编辑、可停用、可回滚、可审计

也就是说：

- 首版不追求“模型被重新训练”
- 首版追求“系统越来越懂你的工作方式，并且这个过程用户可控”

#### 8.6.2 它要解决什么问题

这一能力至少要解决以下真实问题：

1. 用户每次都要重复说明自己的工作背景
2. 用户常做的流程无法被系统主动识别和推荐
3. 输出风格、文档结构、常用模板无法稳定复用
4. 目录访问、危险动作确认、授权边界无法体现个人习惯
5. 系统虽然“有记忆”，但用户不知道记住了什么，也无法安心依赖

#### 8.6.3 个人工作画像的数据模型

生产级版本必须有清晰的数据模型，不能把所有信息都混进一份 MEMORY.md。

建议至少拆成六类：

1. **基础身份画像**
   - 姓名 / 角色 / 部门 / 岗位
   - 工作职责
   - 常用系统
   - 常用文档类型

2. **工作偏好画像**
   - 输出语言偏好
   - 文档结构偏好
   - 汇报风格偏好
   - 表格 / Markdown / PPT 等格式偏好

3. **流程画像**
   - 常做任务
   - 高频操作顺序
   - 常用目录
   - 常用网站 / 系统 / 数据源
   - 常用审批链路

4. **授权习惯画像**
   - 哪类动作通常可以直接允许
   - 哪类动作必须先确认
   - 哪类目录始终禁止
   - 哪类风险动作必须进入审批

5. **知识与模板画像**
   - 高频引用知识
   - 常用模板
   - 偏好的 SOP
   - 常见纠正项

6. **关系与上下文画像**
   - 常协作对象
   - 常处理项目
   - 当前阶段重点任务
   - 时间性工作上下文

#### 8.6.4 学习来源与采集边界

系统不能“偷偷学习一切”，而应明确学习来源与边界。

建议学习来源限定为：

1. 用户明确保存的偏好
2. 会话中被确认有效的总结与纠正
3. 已执行成功的流程与模板
4. 用户授权后的操作轨迹
5. 用户主动沉淀的文档、知识仓内容与工作记录

必须明确不默认学习的内容：

- 未确认的临时聊天噪音
- 敏感凭据
- 私密目录中的原始文件内容
- 用户拒绝授权的动作细节
- 与工作画像无关的偶发操作

#### 8.6.5 学习闭环设计

生产级方案不能只有“记住”，必须形成完整闭环：

1. **捕获**
   - 从会话、流程、执行、审批、知识沉淀中收集候选信号

2. **提炼**
   - 把原始行为提炼成偏好、流程片段、模板建议、规则候选

3. **确认**
   - 低风险项可自动纳入候选
   - 中高风险项必须由用户确认后才进入长期画像

4. **应用**
   - 在新会话、工作台、执行页、流程页中主动推荐

5. **修正**
   - 用户可标记“不适用”“不要再这样做”“仅本项目适用”

6. **治理**
   - 支持停用、回滚、删除、审计

#### 8.6.6 产品页面与交互落点

这项能力必须是显式产品能力，而不是藏在设置细节里。

建议页面落点如下：

1. **知识域**
   - 新增“个人工作画像”子页
   - 展示当前画像摘要、偏好、规则、常用模板、常用知识

2. **工作台**
   - 展示“今日建议动作”“高频流程快捷入口”“与你相关的知识与模板”

3. **会话域**
   - 发起任务时注入相关画像上下文
   - 显示“已应用哪些个人偏好 / 模板 / 规则”

4. **流程域**
   - 将高频任务转为个人流程模板
   - 显示“系统识别到你最近重复执行的流程”

5. **设置 / 权限与安全**
   - 展示授权习惯画像
   - 配置哪些学习结果可自动应用，哪些必须确认

#### 8.6.7 生产级推荐能力

当个人工作画像形成后，系统至少要能做四类推荐：

1. **任务推荐**
   - 识别你常做的工作，给出快捷入口

2. **模板推荐**
   - 根据任务类型推荐文档模板、流程模板、知识模板

3. **上下文推荐**
   - 自动带入相关知识、历史会话、近期文件、相关项目资料

4. **授权建议**
   - 根据你的既往授权习惯，预估哪些动作可能需要确认

#### 8.6.7.A 标题驱动的信息搜集与相关性整理

这是个人工作画像与习惯学习中必须重点支持的高频场景之一。

很多真实办公任务里，用户不会一开始就给出完整需求，而只是给一个标题、主题或一句方向描述，例如：

- “整理一下 xx 行业近期动态”
- “帮我看看这个主题有没有值得跟进的资料”
- “按这个标题搜一下，并整理和我要的内容最相关的信息”

这类场景的目标，不是单纯“浏览器搜索”，而是让系统逐步学会用户的信息搜集方式与相关性判断习惯。

生产级版本应把它定义为：

**标题驱动的信息搜集与相关性整理助手。**

至少需要包含以下能力：

1. **标题意图补全**
   - 用户只给标题时，系统先推断潜在目标
   - 自动补全可能需要的关键词、行业上下文、时间范围、比较维度、排除条件
   - 在不确定时给出最少量澄清，而不是让用户重新完整写一遍需求

2. **搜索策略学习**
   - 学习用户常用搜索源
   - 学习用户常用关键词风格、限定词、排除词
   - 学习用户偏好的信息类型，如新闻、研报、官方文档、社区讨论、政策原文

3. **结果相关性分层**
   - 不只是抓取结果列表，而是判断每条信息与当前目标的相关程度
   - 至少分为：
     - 高相关
     - 中相关
     - 低相关
     - 噪音 / 可忽略

4. **结构化整理输出**
   - 按用户习惯输出固定结构，而不是每次自由发挥
   - 输出结构至少支持：
     - 核心结论
     - 关键证据
     - 高相关信息摘要
     - 可进一步跟进的信息
     - 参考来源列表

5. **偏好纠正与持续学习**
   - 用户可标记“这类信息太泛”“这类来源以后少给我”“这类结构正是我想要的”
   - 系统基于用户的保留、删除、采纳、否定行为持续修正排序与整理逻辑

#### 8.6.7.B 与浏览器、知识、流程的联动要求

这项能力不能孤立实现，必须与其它主线联动：

1. **与浏览器自动化联动**
   - 浏览器负责搜索、打开、提取、抓取候选资料

2. **与知识中心联动**
   - 高相关结果可一键沉淀为知识条目、研究笔记或 Obsidian 文档

3. **与流程中心联动**
   - 常见研究动作可沉淀为“信息搜集流程模板”
   - 例如：标题输入 → 搜索 → 筛选 → 相关性排序 → 结构化总结 → 知识沉淀

4. **与个人工作画像联动**
   - 系统要记住你偏好的信息源、输出结构、相关性判断口径

#### 8.6.7.C 分阶段实施要求

##### P1 基础版

- 标题驱动搜索
- 多结果抓取
- 初步相关性排序
- 固定结构摘要输出

##### P2 学习版

- 学习用户常用信息源与筛选习惯
- 学习用户偏好的整理结构
- 支持用户对相关性结果进行纠正反馈

##### P3 生产级版

- 形成稳定的信息搜集画像
- 可解释为什么某条结果被判定为高相关
- 与知识沉淀、流程模板、权限与安全中心完全联动

#### 8.6.7.D 验收标准

这一能力完成时，至少要同时满足：

1. 用户只给标题或主题时，系统也能启动有效的信息搜集流程
2. 系统能对候选结果进行相关性分层，而不是只罗列搜索结果
3. 输出结果能按用户偏好的固定结构整理
4. 用户能够纠正“哪些相关、哪些不相关”，且系统后续会学习这些反馈
5. 高相关内容可进一步沉淀到知识中心或本地知识仓
6. 用户能够明显感受到系统越来越接近自己的信息搜集与整理习惯

#### 8.6.8 记忆治理与质量控制

这是生产级支持的关键，不然只会越用越乱。

至少要具备：

1. **记忆分层**
   - 会话级短期记忆
   - 个人长期记忆
   - 项目级记忆
   - 团队级知识

2. **有效性控制**
   - 过期策略
   - 冲突检测
   - 重复内容合并
   - 低置信度候选不自动升级为长期画像

3. **人工治理**
   - 可编辑
   - 可停用
   - 可删除
   - 可回滚

4. **适用范围**
   - 全局适用
   - 某个项目适用
   - 某个流程适用
   - 某个会话临时适用

#### 8.6.9 与权限与安全中心的联动

个人工作画像不能绕开权限与安全中心。

必须明确：

1. 系统不能因为“学习到你习惯这样做”就自动突破权限边界
2. 授权习惯只能在已允许的策略框架内生效
3. 危险动作永远服从权限与安全中心的规则
4. 用户必须能看到“这次推荐或默认行为，是基于哪条画像 / 规则 / 历史习惯”
5. 用户习惯沉淀的主数据源应改为**事件流**，而不是继续依赖对话指令本身
6. 后续画像提炼优先使用：
   - 目录访问事件
   - 文件操作事件
   - 站点访问事件
   - 审批 / 确认事件
   - 纠偏与回退事件

#### 8.6.10 与知识中心、流程中心的联动

这项能力必须和已有主线打通：

1. **与知识中心联动**
   - 高频知识引用可进入个人工作画像
   - 画像中的模板偏好可反向影响知识沉淀格式

2. **与流程中心联动**
   - 高频重复操作自动形成流程候选
   - 用户确认后升级为个人流程模板

3. **与会话中心联动**
   - 新会话自动带入相关偏好、项目背景、输出格式习惯

4. **与 Obsidian / 本地知识仓联动**
   - 用户常用知识仓目录、模板、标签、Frontmatter 可进入画像

#### 8.6.11 分阶段实施方案

##### A. P1 基础可用版

必须完成：

- 个人偏好配置
- 用户资料可视化
- 基础长期记忆开关
- 会话中的画像上下文注入
- 常用模板与常用目录的显式配置

完成后，系统至少能做到“知道你是谁、常用什么、偏好什么”。

##### B. P2 学习闭环版

必须完成：

- 高频流程识别
- 授权习惯候选
- 模板推荐
- 候选记忆确认面板
- 记忆治理与审计

完成后，系统至少能做到“开始学习你怎么工作，并且这个过程用户可控”。

##### C. P3 生产级画像版

必须完成：

- 个人工作画像中心
- 长短期记忆分层
- 项目 / 任务 / 流程级适用范围
- 推荐解释能力
- 可编辑 / 可回滚 / 可停用治理

完成后，系统才可以称为“日常熟悉你工作流程的生产级桌面智能体”。

#### 8.6.12 验收标准

个人工作画像与习惯学习中心完成时，至少要同时满足：

1. 系统能稳定保存并应用个人偏好、输出风格、常用模板与常用目录
2. 系统能从高频成功工作中提取流程候选，而不是只保存零散记忆
3. 用户能清楚看到系统学到了什么，并可编辑、停用、删除、回滚
4. 所有长期画像都具备来源说明、适用范围与更新时间
5. 画像推荐不会绕开权限与安全中心
6. 会话、流程、知识、授权习惯之间能形成联动闭环
7. 用户能够明显感受到“系统越来越懂我的工作方式”，且不会产生失控感

#### 8.6.13 明确不采用的方案

首版明确不采用以下路线：

- 直接把“记忆开关”当作生产级习惯学习能力
- 用不可解释的自动学习替代用户确认
- 将所有偏好、流程、规则混写在单一 Markdown 中长期堆积
- 在没有治理、回滚、审计前就默认自动应用高风险习惯
- 把“熟悉你的工作方式”理解成必须先做模型微调

结论：

**Ti Work 要实现“熟悉你日常工作流程”的生产级能力，核心不是先训练模型参数，而是先建设个人工作画像与习惯学习中心，让系统在可视化、可确认、可治理的前提下，持续学习你的任务模式、输出偏好、流程习惯与授权边界。**

## 9. P4：自修复与自进化

### 9.1 阶段目标

让平台具备“越用越稳定、越用越懂组织”的能力。

### 9.2 本阶段要完成的能力

#### A. 自修复

必须形成：

- 工具失败分类
- 失败诊断
- 自动重试策略
- 修复建议
- 回滚建议

用户效果：

- 系统不只报错，还能解释、建议、辅助恢复

#### B. 自进化

必须形成：

- 基于企业知识与员工行为的模板优化
- 高频工作自动总结
- 低效流程识别
- 模板与规则持续升级

用户效果：

- 平台逐步具备组织学习能力

### 9.3 P4 交付物

- 执行失败诊断中心
- 修复策略中心
- 模板 / 规则优化推荐
- 组织经验增量沉淀机制

### 9.4 P4 完成标准

必须同时满足：

1. 常见失败能够自动诊断并给出下一步
2. 高频流程可得到持续优化
3. 企业知识、流程、模板、岗位画像形成自增强关系

## 10. 阶段依赖关系

```
P0 Hermes 底座稳定
  ↓
P1 企业办公核心闭环
  ↓
P2 数据与审计闭环
  ↓
P3 企业知识与员工技能沉淀
  ↓
P4 自修复与自进化
```

解释：

- 没有 P0，就没有可靠执行底座
- 没有 P1，就没有真实办公入口
- 没有 P2，就无法进入企业受控场景
- 没有 P3，就无法形成组织资产
- 没有 P4，就谈不上长期自增长

## 11. 每阶段验收问法

后续每阶段评审都必须回答四个问题：

1. 这阶段到底新增了哪些页面和能力？
2. 用户能完成什么新的真实工作？
3. 哪些数据 / 知识 / 规则开始被沉淀？
4. 什么证据证明阶段已经完成？

如果回答不清，就说明阶段定义还不够具体，不能进入开发。

## 12. 当前立即执行事项

当前必须立刻执行的，不是 P1/P2 开发，而是安装版 P0 收口：

1. 产出安装版方案，明确安装路径、Hermes 工作目录、资源布局与安装步骤
2. 在安装过程中一并准备 Hermes 网关运行环境，而不是全部留到首启自举
3. 完成“首次打开即对话 / 首次打开即引导配置 API Key”的产品闭环
4. 以本文件为后续功能收敛边界
5. 后续产品设计全部围绕 6 个一级菜单域收口
6. 安装版 P0 通过后再进入 P1 详细原型与任务拆解

---

## 13. 结论

Ti Work 的正确方向不是“再堆更多功能页”，而是按下面这条主线推进：

**先把安装版执行底座打稳，让用户安装成功后就能对话，再把工作入口收口，再把文件 / 浏览器 / 流程 / 数据 / 知识打成闭环，最后让平台具备企业级沉淀、自修复与自进化能力。**

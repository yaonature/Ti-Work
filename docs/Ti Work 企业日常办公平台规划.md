# Ti Work 企业日常办公平台规划

> 状态：实施规划文档（2026-08-15 更新）
> 适用范围：Ti Work 桌面端后续产品规划、研发排期、页面收口、验收标准
> 当前最高优先级：**P0 免安装版链路已打通，下一步必须完成安装版内置 Hermes 网关闭环，确保用户安装成功后即可进入可对话状态**

---

## 1. 产品重新定义

Ti Work 后续不是继续做“功能很多的 AI 桌面工具”，而是做一套面向企业员工真实日常工作的桌面办公平台。

目标形态：

- 员工可以用它处理文件、网页系统、知识库、流程任务、数据库、日常文档与表格类工作
- 平台可以沉淀企业知识、团队经验、岗位 SOP、员工技能与常见执行模板
- 平台可以把“单次会话”升级成“可复用的业务执行能力”
- 平台逐步具备自修复、自优化、自进化能力

一句话定义：

**Ti Work = 企业员工的 AI 办公操作台 + 企业知识 / 流程 / 技能沉淀平台。**

---

## 2. 当前问题

当前产品不是能力绝对不足，而是存在三个核心问题：

1. **安装版尚未闭环**：免安装验证已通过，但正式安装版还没有做到“安装阶段就把 Hermes 网关准备好，安装后首启即可对话”
2. **能力太散**：左侧一级菜单过多，用户无法快速识别主路径
3. **缺少闭环**：文件、浏览器、记忆、数据库、流程、审计还没有串成企业办公闭环

因此后续路线必须先做：

- 底座稳定
- 菜单收口
- 核心工作闭环
- 组织沉淀闭环

---

## 3. 左侧菜单目标结构

当前侧边栏入口太多，开发者视角过重。后续必须把前台菜单做成：

**稳定通用骨架 + 行业工作包命名映射 + 角色裁剪 + 个人习惯微调。**

这里的“菜单”指的是用户前台看到的产品菜单，而不是底层技术能力分组。  
也就是说，前台菜单必须是非技术性的工作语言，不能把 `会话 / 执行 / 多智能体 / MCP / 血缘` 这类术语直接暴露给最终办公用户做一级导航。

### 3.1 通用产品骨架的目标一级菜单

前台一级菜单固定为 6 个槽位，长期不随行业频繁变化：

| 菜单 | 核心定位 | 主要承载内容 |
|---|---|---|
| 工作台 | 今日工作入口 | 今日待办、提醒、最近工作、今日摘要、快捷动作 |
| 业务 | 当前真正要处理的工作 | 业务任务、任务助手、检索、分析、专项工作 |
| 文档 | 各类材料与输出物 | 文档起草、审阅、比对、文件处理、模板、报表 |
| 知识 | 个人与组织沉淀 | 知识库、规则、经验、工作画像、模板偏好 |
| 协作 | 流转、审批与团队配合 | 任务流转、审批、协同、流程、自动化 |
| 管理 | 治理与运营 | 权限、安全、审计、日志、分析、运行状态 |

底部固定：

- 设置
- 帮助 / 文档

说明：

- `管理` 默认按角色显示，不必对所有普通用户展开
- `搜索` 是全局入口，不计入一级菜单
- 行业包主要改变的是 `业务` 与 `文档` 的命名和内容，`工作台 / 知识 / 协作 / 管理` 尽量保持稳定

- 被收进新的一级菜单骨架
- 在二级菜单或页内功能中以更贴近工作语言的方式表达
- 只在管理员、高级用户或专业模式中显式暴露必要的技术细节

### 3.6 菜单收口与实施原则

- 一级菜单长期固定为 `工作台 / 业务 / 文档 / 知识 / 协作 / 管理`
- 行业包主要通过“菜单别名 + 首页模块 + 二级菜单 + 默认模板/知识源/流程”体现差异
- 不再继续新增一级菜单
- 实验能力默认不进入一级导航
- 二级功能放入域页面内部 tab / 面板
- 菜单首先按“办公任务”组织，而不是按“技术模块”组织
- 开发实施时，优先改导航分组与命名，不要求第一阶段重写全部页面
- `管理` 为角色可见项，普通用户可按需要弱化或默认隐藏

#### 3.7.2 第一阶段必须做的导航改造动作

第一阶段目标不是重做全部页面，而是先把用户看见的导航语言和结构改对。

必须完成：

1. 侧边栏一级分组改为：
   - 工作台
   - 业务
   - 文档
   - 知识
   - 协作
   - 管理

2. 以下技术性名称不再作为一级菜单出现：
   - 会话
   - 文件
   - 终端
   - 多智能体
   - 任务编排
   - 记忆
   - 技能
   - 用户档案
   - 模式与纠正
   - 审计记录
   - 日志
   - 运维视图

3. `设置` 与 `帮助 / 文档` 固定到底部系统区

4. `管理` 默认按角色可见：
   - 普通用户可弱化或隐藏
   - 管理员、主管、企业治理角色正常显示

5. 当前页面内容先复用，不要求第一阶段改完页内结构

#### 3.7.3 第二阶段整理动作

第一阶段完成后，再进入第二阶段收口：

1. 为通用办公包补齐统一的二级导航名称
2. 为律所、财务、人事等行业包做前台别名映射
3. 把页内 tab、标题、按钮文案也逐步从技术术语替换成业务术语
4. 将 `任务 / 待办 / 多智能体 / 编排` 在视觉上收敛为同一协作域体验
5. 将 `记忆 / 技能 / 档案 / 规则 / Obsidian / 工作画像` 逐步整成统一知识域

#### 3.7.4 建议的研发实施顺序

建议按以下顺序推进，避免一次性改动过大：

##### A. 第一步：只改导航配置和名称

- 修改侧边栏分组
- 修改显示名称
- 调整 icon 和排序
- 不改现有路由文件

##### B. 第二步：补二级入口与页头名称

- 页面标题与面包屑改名
- 页内 tab 与操作按钮改成业务术语
- 把重复入口合并到统一二级菜单

##### C. 第三步：加入行业别名与工作模式切换

- 通用办公包名称先上线
- 再接入律所、财务、人事等行业工作包别名
- 菜单名称、首页卡片、默认模板随工作模式切换

##### D. 第四步：再做深层页面重构

- 只有在导航收口稳定后，才重做复杂页面
- 避免一边改路由、一边改菜单、一边改页面信息架构，导致工作量失控

#### 3.7.5 当前阶段明确不做的事

为了保证收口效率，这一步先不做：

- 不重写全部页面内部逻辑
- 不强制修改所有路由路径
- 不一次性做完所有行业包的完整首页
- 不把实验能力、调试能力、研发能力重新抬成一级菜单

#### 3.7.6 本节作为开发实施依据的使用方式

后续菜单导航改版开发，必须以本节为基准：

1. 先查当前路由归属到哪个一级/二级菜单
2. 再判断该入口是保留、改名、归并还是弱化
3. 若新增页面，必须先回答它属于：
   - 工作台
   - 业务
   - 文档
   - 知识
   - 协作
   - 管理
4. 若无法明确归属，说明信息架构尚未设计清楚，不能直接加入口

## 5. P0：Hermes 首装与执行底座稳定

### 5.0 当前状态

P0 已完成第一阶段闭环：

- 免安装版 / `win-unpacked` 已可自动拉起 Hermes 网关
- `8642` 健康检查可通过
- 模型列表可正常返回
- 首条消息已可真实发送并收到回复

但对正式交付来说，P0 还差最后一个必须完成的版本：

- **安装版闭环**

也就是：用户在安装 Ti Work 的过程中，就已经把 Hermes 网关相关依赖、运行目录、配置骨架一并准备好；安装成功后首次打开应用，要么直接可对话，要么明确提示配置 API Key，配置完成后立即可对话。

### 5.1 阶段目标

让桌面端正式安装版真正达到：

- 安装过程中就完成 Hermes 网关所需资源与目录准备
- 用户安装成功后第一次打开即可进入可用状态，而不是再经历长时间自举等待
- 若未配置模型 API Key，首启必须给出清晰、唯一、可完成的配置引导
- 用户完成 API Key 配置后，可立即稳定完成第一条消息

### 5.2 本阶段必须完成的功能

1. **安装版后端稳定启动**
   - 不依赖用户机器外部 `node.exe`
   - 使用安装包自身 runtime 拉起本地后端

2. **安装过程中完成 Hermes 预装**
   - 安装包内置 Hermes 固定版本资源
   - 安装程序在安装阶段完成 Hermes 工作目录准备
   - 安装程序在安装阶段完成 gateway 所需依赖与运行时初始化
   - 安装结束时，本地已具备可启动 Hermes 网关的最小完整环境

3. **首启即用 / 首启即配**
   - 若本地已有有效模型配置，首次打开应用即可直接对话
   - 若缺少 API Key，不允许只给模糊报错，必须进入明确配置引导
   - 配置页只保留完成对话所需最小必要项：provider / model / baseUrl / apiKey
   - API Key 保存成功后，无需手工重启整套链路即可开始对话

4. **安装状态和失败原因可表达**
   - 安装阶段失败时要明确告诉用户是哪个安装步骤失败
   - 首启阶段失败时要能区分：网关未启动、模型未配置、配置无效
   - 禁止再出现“网关已启动但实际不可对话”的假成功状态

5. **路径与版本策略固定**
   - 严禁安装阶段回退到在线拉取 Hermes 源码
   - 严禁依赖用户本机 Git / Node 外部环境
   - 安装版与免安装验证版必须使用同一套固定版本 Hermes 资源策略

### 5.3 页面 / 交互结果

- 安装过程中：
  - 若 Hermes 预装仍在进行，安装器内必须有明确进度或步骤提示
  - 不允许把 Hermes 安装问题全部留到用户首次打开应用后再处理
- 首次打开应用后：
  - 能直接进入工作界面
  - 若网关已就绪且模型已配置，可直接对话
  - 若缺少模型 API Key，显示清晰配置引导，而不是离线报错
- 用户配置 API Key 后：
  - 无需手工执行命令
  - 无需理解 Hermes 细节
  - 回到会话页即可正常发送消息

### 5.4 完成标准

必须同时满足：

1. 安装版安装完成后，本地 Hermes 网关运行环境已准备完毕
2. 首次打开 `Ti Work.exe` 时，不再依赖长时间首装 bootstrap 才能进入可用状态
3. 若模型配置已存在，用户首次进入会话页即可直接成功发送一条消息
4. 若模型配置不存在，系统必须明确提示配置 API Key，且配置成功后立即可发送第一条消息
5. 用户全程无需手工执行任何命令
6. 不再出现误导性的“执行引擎未连接”或“网关失败”假报错

### 5.5 安装版实施重点

这一阶段的核心不是继续优化免安装体验，而是把正式安装流程做成真正的产品闭环。

#### A. 安装程序要负责什么

- 选择安装路径
- 写入 Ti Work 应用主体
- 写入 Hermes 固定版本资源
- 完成 Hermes 工作目录初始化
- 生成网关最小配置骨架
- 预置运行所需 token / env / config 骨架
- 完成必要依赖准备与网关可启动性检查

#### B. 首次启动要负责什么

- 检查 Hermes 网关是否可直接启动
- 检查本地模型配置是否完整
- 若缺少 API Key，则进入配置引导，而不是报错
- 若配置完整，则直接进入可对话状态

#### C. 用户体验目标

- 用户理解的是“安装 Ti Work”，而不是“再安装一个 Hermes”
- 用户不需要知道 Hermes 工作目录、bootstrap、manifest、gateway 这些技术概念
- 对用户来说，安装成功的标准就是：打开后能开始对话；若缺 Key，就把 Key 配完后立刻能对话

### 5.6 未完成前禁止推进的内容

- 浏览器自动化主卖点
- 数据库产品化
- 移动端主路径
- 企业能力对外宣发
- 一级菜单继续扩张

## 6. P1：企业办公核心闭环

### 6.1 阶段目标

让 Ti Work 从“能聊天”升级为“能处理员工日常工作”。

P1 解决的是：员工每天打开软件，到底能拿它完成什么具体工作。

### 6.2 本阶段要形成的产品能力

#### A. 工作台

必须形成一个真正的“今日工作入口”页面，至少包含：

- 今日待办
- 最近文件
- 最近会话
- 最近流程
- 工作提醒 / 审批提醒
- 今日工作摘要

用户效果：

- 打开软件第一眼就知道今天要做什么
- 不需要先理解系统结构，再决定去哪个页面

#### B. 会话中心

会话页要从普通对话框升级为“任务发起中心”：

- 支持从文件、流程、网页任务发起会话
- 支持结构化任务上下文
- 支持附件、指令模板、会话标签
- 支持历史回溯

用户效果：

- 会话不只是聊天，而是办公任务的入口

#### C. 执行中心

执行域至少要覆盖四件事：

1. 文件处理
2. 浏览器自动化
3. 终端执行
4. 数据库操作入口（先做基础版）

用户效果：

- 用户不是只能“问 AI”，而是可以让它真正做事

#### D. 流程中心

把离散能力转成可复用流程：

- 任务
- 编排
- 多智能体
- 定时任务
- 流程模板

用户效果：

- 重复工作不再一遍遍重新描述
- 常见工作可以保存成模板

#### E. 知识中心

先形成“个人+团队基础沉淀”：

- 记忆
- 技能
- 用户档案
- 规则 / 纠正项

用户效果：

- 平台开始记住企业和员工怎么工作

#### F. 权限与安全中心（最小版）

必须先给用户一个可视化、可理解、可控制的安全边界，而不是把授权逻辑藏在配置文件或弹窗细节里。

P1 最小版至少要具备：

- 文件系统目录白名单 / 黑名单
- 工具级授权开关（文件、终端、浏览器、数据库、网络、MCP）
- 危险动作二次确认
- 会话级临时授权
- 最近授权记录与最近危险动作提示

用户效果：

- 用户知道智能体当前能做什么、不能做什么
- 用户可以直观看到哪些目录允许访问，哪些目录禁止访问
- 用户在关键操作前有明确确认，而不是事后才发现被执行

### 6.3 P1 交付物

必须至少形成：

- 新一级菜单结构原型
- 工作台页面 v1
- 执行中心页面 v1
- 流程中心页面 v1
- 知识中心页面 v1
- 权限与安全中心 v1
- 工作场景模式中心 v1
- 会话作为任务发起中心的交互收口

### 6.4 P1 完成标准

必须同时满足：

1. 一个普通企业员工无需懂技术，也能看懂主菜单
2. 用户能完成至少 3 类真实办公闭环：
   - 文件整理 / 改写 / 汇总
   - 网页系统查询 / 填报 / 提取
   - 重复工作保存为流程模板
3. 不必在十几个菜单之间来回找功能
4. 用户能清楚配置智能体的授权边界，并理解危险动作何时会被拦截或确认
5. 用户安装后可按岗位初始化工作模式，后续也能随时切换场景而不丢失个人数据与治理边界

### 6.5 P1 不做什么

- 先不追求复杂企业中台
- 先不做极重的数据库治理
- 先不做大规模组织分析能力

### 6.6 工作场景模式切换与菜单自适配机制

Ti Work 作为通用桌面办公智能体，不能假设用户永远只处于一个固定场景。

真实办公里，用户经常会出现：

- 同一个人跨行业职能处理事务
- 同一个岗位在不同时间段切换不同工作模式
- 同一个用户同时存在“通用办公模式”“项目专项模式”“行业专项模式”
- 用户岗位、职责、团队边界发生变化

因此，首启时进行一次岗位初始化是合理的，但产品不能停留在那里，必须支持：

**首次初始化 + 后续随时切换场景 + 系统智能建议切换。**

#### 6.6.1 方案结论

Ti Work 菜单不能写死为单一行业版本，而应采用：

1. **稳定通用骨架**
   - 一级菜单骨架长期稳定

2. **工作模式层**
   - 不同行业 / 岗位 / 项目场景加载不同工作模式

3. **角色裁剪层**
   - 普通员工、主管、管理员看到的菜单范围不同

4. **个人习惯微调层**
   - 用户自己的常用模块、模板、知识源、快捷动作可继续自适配

也就是说：

- 安装包只有一个通用产品壳
- 菜单、首页、默认模板、默认知识源、默认流程通过工作模式动态适配

#### 6.6.2 首次初始化机制

首次打开应用时，系统应提供一个轻量的“工作模式初始化”流程，而不是直接丢给用户一套固定通用菜单。

初始化至少应采集：

1. **行业 / 场景**
   - 通用办公
   - 律所
   - 财务
   - 人事
   - 其他行业

2. **岗位角色**
   - 普通执行角色
   - 助理 / 专员
   - 主管 / 负责人
   - 管理员

3. **高频工作类型**
   - 搜索资料
   - 写文档
   - 处理审批
   - 管理文件
   - 跑固定流程
   - 知识沉淀

初始化完成后，系统应自动决定：

- 一级菜单别名
- 首页卡片
- 默认模板集
- 默认知识源
- 默认流程集
- 默认快捷动作
- 默认权限建议

#### 6.6.3 后续场景切换机制

生产级产品必须支持后续场景切换，而不是只能首装配置一次。

建议支持三种切换层级：

1. **长期默认场景**
   - 用户最常用的主模式
   - 例如：通用办公、律所办案、财务处理

2. **临时场景切换**
   - 某一阶段短期切换
   - 例如：本周临时处理合同审阅或月结任务

3. **任务级场景**
   - 针对当前任务指定模式
   - 例如：这次按“财务月结模式”执行

#### 6.6.4 场景切换后哪些会变化

工作模式切换后，允许变化的包括：

- 菜单名称
- 菜单排序
- 首页卡片内容
- 默认模板
- 默认知识源
- 推荐流程
- 默认快捷动作
- 行业术语表达

这些变化属于“工作视图与默认策略变化”，是合理且必要的。

#### 6.6.5 场景切换后哪些不能被覆盖

场景切换不能破坏用户的基础数据与治理边界。

不应被直接覆盖的包括：

- 用户全局身份信息
- 全局权限与安全底线
- 全局禁区目录
- 核心危险动作规则
- 审计记录
- 历史知识资产

结论上要坚持：

**场景切换是切换工作模式，不是重置用户。**

#### 6.6.6 产品页面与交互方式

必须提供一个明确可见的“工作模式切换器”，而不是依赖隐藏设置。

建议落点如下：

1. **顶栏 / 工作台顶部**
   - 作为当前模式显示与快速切换入口

2. **设置页中的“工作模式”配置页**
   - 查看当前模式
   - 调整行业、岗位、高频工作
   - 恢复默认模式
   - 管理自定义模式

3. **任务发起时的模式选择**
   - 当前任务可临时指定模式

#### 6.6.7 自动建议切换机制

系统应支持“智能建议切换”，但不应擅自自动切换。

例如：

- 你最近连续在处理报销、付款、对账任务，是否切换到“财务处理模式”？
- 你最近连续在检索法规、起草意见书，是否切换到“律所办案模式”？

产品原则应是：

- 系统给出建议
- 用户显式确认
- 记录本次切换来源与是否长期生效

#### 6.6.8 与菜单自适配的关系

菜单适配不应靠为每个行业单独做一套安装包，而是靠“骨架稳定、表达可变”实现。

推荐模型如下：

1. **骨架层**
   - 工作台
   - 业务
   - 文档
   - 知识
   - 协作
   - 管理（按角色显示）

2. **模式映射层**
   - `业务` 可按模式显示为：
     - 办案
     - 财务
     - 人事
     - 通用业务

3. **个人微调层**
   - 常用菜单置顶
   - 隐藏低频模块
   - 收藏快捷动作
   - 首页卡片重排

#### 6.6.9 与个人工作画像的联动

工作模式切换必须和“个人工作画像与习惯学习中心”打通。

至少要支持：

- 不同场景下的偏好隔离
- 不同场景下的模板偏好
- 不同场景下的知识源偏好
- 不同场景下的授权习惯差异

例如：

- 用户在“财务模式”下偏好 Excel 输出
- 用户在“律所模式”下偏好 Markdown 研究纪要
- 用户在“通用办公模式”下更强调审批提醒和任务摘要

#### 6.6.10 商业分层与定价策略

工作场景模式不只是产品体验问题，也直接影响商业模式。

这里必须明确一个原则：

**不要按菜单收费，要按能力包、使用成本和行业价值收费。**

原因很直接：

- 用户不能接受“只是多了一个菜单名字就要额外付费”
- 但用户可以理解“某个行业模式背后附带了更强模板、知识包、流程包和治理能力，因此价格更高”

也就是说：

- `工作场景模式` 是产品机制
- `行业工作包`、`企业治理能力`、`高成本执行能力` 才是主要商业分层点

##### A. 默认开通策略

建议默认开通一个：

- **通用办公模式**

原因：

- 用户安装后必须立刻可用
- 不能因为未购买行业包而卡在初始化阶段
- 通用模式是产品体验入口，也是后续升级行业模式的基础

##### B. 推荐商业分层

建议分为四层：

1. **基础版**
   - 默认通用办公模式
   - 基础工作台
   - 基础文档处理
   - 基础知识沉淀
   - 基础权限与安全能力

2. **专业版**
   - 多工作模式切换
   - 更强个人工作画像
   - 更多模板、流程与知识源接入
   - 更强浏览器 / 文件处理能力

3. **行业工作包**
   - 律所工作包
   - 财务工作包
   - 人事工作包
   - 其它行业包
   - 每个包至少包含：
     - 行业首页
     - 行业模板
     - 行业流程
     - 行业知识源
     - 行业术语表达

4. **企业版**
   - 审批
   - 审计
   - 权限与安全中心高级治理
   - 组织级工作模式下发
   - 多人协作
   - 成本控制与席位管理

##### C. 适合做收费差异的能力

适合拉开价格差异的，不是菜单名称，而是以下能力：

- 行业模板库
- 行业知识包
- 行业流程包
- 深度浏览器自动化
- 大批量文档处理
- OCR / 解析
- Obsidian / 本地知识仓高级联动
- 个人工作画像高级学习能力
- 审批、审计、组织级权限治理

##### D. 不建议做收费门槛的基础能力

以下能力不应被切得太碎，也不适合做成“没有就无法放心使用”的收费门槛：

- 基础工作模式初始化
- 基础场景切换
- 基础权限与安全能力
- 基础危险动作确认
- 基础审计可见性

原因是：

- 没有这些基础能力，用户很难放心把桌面智能体真正用于办公
- 这些应该作为产品可信度的一部分，而不是纯增值障碍

##### E. 价格表达方式

用户应该感知为：

- 我买的是 **Ti Work 通用办公智能体**
- 如果我是律师，我再开 **律所工作包**
- 如果我是财务，我再开 **财务工作包**
- 如果我是企业，我再开 **企业治理版**
- 如果我需要更强自动化或更多额度，再加 **高级执行包 / 用量包**

这样表达比“按菜单收费”清楚得多，也更符合办公软件采购逻辑。

##### F. 产品与商业的一致性原则

最终必须坚持：

1. 通用模式开箱可用
2. 行业模式通过行业工作包体现差异化价值
3. 企业治理能力作为更高层级收费点
4. 高成本执行能力可做额度或高级版收费
5. 不把基础安全能力做成缺失项

#### 6.6.11 分阶段实施方案

##### A. P1 最小版

必须完成：

- 首次工作模式初始化
- 工作模式切换器
- 行业 / 岗位驱动的菜单别名
- 首页卡片随模式变化
- 默认模板与默认知识源随模式变化

##### B. P2 增强版

必须完成：

- 临时模式切换
- 任务级模式指定
- 系统建议切换
- 模式切换日志与审计
- 模式级权限建议

##### C. P3 生产级版

必须完成：

- 自定义工作模式
- 多模式习惯学习
- 模式级画像治理
- 模式级模板 / 流程 / 知识联动
- 组织级下发默认工作模式

#### 6.6.12 验收标准

工作场景模式切换与菜单自适配机制完成时，至少要同时满足：

1. 用户首次进入时可快速完成岗位 / 行业初始化
2. 用户后续可随时切换工作场景，而不需要重新安装或重新配置全部产品
3. 切换场景后，菜单名称、首页内容、模板与知识源可同步变化
4. 切换场景不会破坏全局安全策略、审计记录与核心身份信息
5. 系统可基于使用行为建议切换，但不会擅自替用户切换
6. 同一用户在不同模式下可形成不同的工作习惯画像
7. 用户能理解“当前为什么看到这套菜单与推荐内容”

让平台从“个人好用”升级到“组织可放心使用”。

P2 关注的是：执行行为必须留痕、可审计、可恢复、可治理。

### 7.2 本阶段要完成的能力

#### A. 数据库操作工作台

用户效果：

### 7.3 P2 交付物

- 数据库操作页 v1
- 审计中心 v1

- 执行结果导出 / 留痕能力

### 7.4 P2 完成标准

必须同时满足：

1. 文件 / 浏览器 / 数据库 / 流程执行均可留痕
2. 管理者可以查到谁做了什么
3. 高风险动作具备审批或限制机制
4. 用户能查看失败原因和执行历史

### 7.5 权限与安全中心生产级方案

权限与安全中心不是一个附属设置页，而是 Ti Work 进入真实办公和企业场景的前置条件。

它要解决的核心问题是：

- 智能体什么时候默认可执行
- 什么时候必须先征得授权
- 哪些目录可以访问，哪些目录必须禁止
- 哪些动作属于危险动作，必须二次确认或审批
- 谁授权了什么、执行了什么、失败了什么，如何追溯

一句话定义：

**权限与安全中心 = Ti Work 的智能体边界控制、风险提示、授权审批与审计留痕的统一中枢。**

#### 7.5.1 产品定位

权限与安全中心要分成两个层次：

1. **设置层的个人权限中心**
   - 面向个人用户和当前工作空间
   - 负责日常授权边界、目录权限、工具开关、危险动作确认

2. **管理层的组织治理中心**
   - 面向企业管理员或团队负责人
   - 负责审批规则、组织级策略、审计回放、高危动作门禁

也就是说：

- `设置` 负责“我允许智能体做什么”
- `管理` 负责“组织允许智能体做到什么程度，以及出了问题如何追溯”

#### 7.5.2 菜单与页面落点

这一能力必须做成可视化菜单，而不是隐藏在配置文件中。

建议菜单落点如下：

1. **设置**
   - 权限与安全
   - 文件系统授权
   - 工具授权
   - 危险动作确认
   - 隐私与数据范围

2. **管理**
   - 审批策略
   - 审计记录
   - 高危动作规则
   - 组织级安全策略

#### 7.5.3 核心边界模型

首版就要明确采用“默认受控、按范围授权、按风险升级确认”的模型。

边界控制至少分四层：

1. **资源范围**
   - 文件系统目录
   - 浏览器网站范围
   - 数据库连接范围
   - 网络访问范围
   - MCP 服务范围

2. **动作类型**
   - 读取
   - 创建
   - 修改
   - 删除
   - 执行
   - 导出
   - 推送 / 发布

3. **风险等级**
   - 低风险：可直接执行或按用户模式处理
   - 中风险：需显式确认
   - 高风险：需二次确认或进入审批

4. **授权时效**
   - 仅当前一步
   - 仅当前任务
   - 仅当前会话
   - 持久策略

#### 7.5.4 文件系统权限模型

文件系统是桌面端最敏感、用户最关心的边界之一，必须可视化配置。

至少要支持：

1. **目录白名单**
   - 用户明确允许智能体访问的目录
   - 可针对目录配置不同权限级别

2. **目录黑名单**
   - 明确禁止访问的目录
   - 黑名单优先级高于白名单

3. **目录权限级别**
   - 只读
   - 可创建
   - 可修改
   - 可删除

4. **默认禁区**
   - 系统目录默认禁止访问，如 `C:\Windows`
   - 应用安装目录和系统程序目录默认禁止写入
   - `.git`、`.obsidian`、凭据目录、密钥目录默认禁止写入
   - 用户未授权的盘符或根目录默认不得全盘开放

5. **可视化表达**
   - 目录树选择器
   - 权限标签
   - 风险说明
   - 最近访问记录

#### 7.5.5 工具授权模型

除了文件系统，还必须控制智能体可调用的工具范围。

至少需要支持以下工具分类：

- 文件系统
- 终端
- 浏览器自动化
- 数据库
- 外部网络请求
- MCP 服务
- Git 操作

每类工具都应支持四种授权模式：

- 始终允许
- 每次询问
- 高危时询问
- 始终禁止

#### 7.5.6 危险动作识别与提示

危险动作不能只靠开发者心里有数，必须产品化定义并显式提示。

至少应纳入危险动作的包括：

- 删除文件或目录
- 批量改写文件
- 执行 Shell / PowerShell 命令
- 安装依赖或修改运行环境
- 写入数据库
- 对外网发送敏感内容
- Git 提交、合并、推送
- 修改系统配置或应用配置

每种危险动作至少要支持：

- 风险提示文案
- 执行前确认
- 高危动作二次确认词
- 是否允许加入长期策略

#### 7.5.7 授权交互方式

这块必须可视化，而不是散落在零碎弹窗里。

建议提供三层交互：

1. **全局策略配置**
   - 用户在设置页统一配置默认授权模式

2. **运行时确认面板**
   - 执行前清楚显示：
     - 准备做什么
     - 涉及哪些目录 / 工具 / 网站 / 数据库
     - 风险等级
     - 本次授权作用范围

3. **会话级临时授权**
   - 当前一步允许
   - 当前任务允许
   - 当前会话允许
   - 永久加入规则

#### 7.5.8 审批与组织级治理

当 Ti Work 进入团队或企业环境，光有个人确认还不够，必须支持审批。

P2 生产级版本至少要支持：

1. 高危动作审批
   - 删除共享目录
   - 批量写库
   - 大范围浏览器自动化提交
   - 外发数据

2. 组织级策略下发
   - 管理员统一规定禁区目录
   - 管理员统一规定禁止工具
   - 管理员统一规定高危动作审批门槛

3. 角色差异化策略
   - 普通员工
   - 高级操作者
   - 管理员
   - 审批人

#### 7.5.9 审计与回放要求

权限与安全中心必须与审计中心打通，不然就只有“拦截”，没有“可追责”。

至少要记录：

- 谁发起了动作
- 使用了哪个智能体 / 工具
- 动作发生时间
- 访问了哪些路径 / 网站 / 数据源
- 最终是否执行成功
- 是否经过确认或审批
- 审批人是谁
- 失败原因是什么

高危动作必须支持回放式查看，至少能重建：

- 原始意图
- 授权决策
- 实际执行动作
- 最终结果

#### 7.5.10 分阶段实施方案

##### A. P1 最小可用版

必须完成：

- 权限与安全设置页
- 文件系统白名单 / 黑名单
- 工具级授权开关
- 危险动作确认弹层
- 会话级临时授权
- 最近授权与最近危险动作记录

完成后，普通用户至少能清楚回答：

- 智能体当前能访问哪些目录
- 智能体当前能调用哪些工具
- 哪些动作会先问我
- 哪些动作绝对不允许执行

##### B. P2 生产治理版

必须完成：

- 权限与安全中心 v2
- 审批策略页
- 组织级安全策略
- 高危动作规则中心
- 审计记录与回放
- 角色差异化权限模型

完成后，平台才具备企业可控的安全边界。

#### 7.5.11 验收标准

权限与安全中心完成时，至少要同时满足：

1. 用户无需修改配置文件，即可可视化配置智能体授权边界
2. 用户可明确配置目录白名单 / 黑名单与不同读写级别
3. 用户可明确配置文件、终端、浏览器、数据库、网络、MCP 等工具权限
4. 危险动作在执行前必须有清晰提示，并支持二次确认
5. 用户可进行一步 / 任务 / 会话 / 持久策略四类授权
6. 高危动作具备审计记录，企业场景下可配置审批
7. 普通用户能够理解系统为什么允许、拦截或要求确认某个动作

#### 7.5.12 明确不采用的方案

首版明确不采用以下路线：

- 把权限规则只做成隐藏配置文件
- 智能体默认拥有全盘文件系统写权限
- 高危动作仅靠开发者硬编码，不给用户可见规则
- 只有拦截弹窗，没有授权范围和审计记录

结论：

**权限与安全中心必须作为 Ti Work 的正式产品能力进入设置与管理体系，并以可视化配置、目录边界、工具授权、危险动作确认、审批与审计的组合方式，为智能体建立用户可理解、企业可治理的执行边界。**

### 8.1 阶段目标

### 8.2 本阶段要完成的能力

要沉淀：

用户效果：

### 8.3 P3 交付物

- 企业知识中心 v1
- Obsidian 知识仓整合 v1
- 个人工作画像与习惯学习中心 v1

### 8.4 P3 完成标准

必须同时满足：

1. 新人能依赖系统快速找到企业知识
2. 老员工的经验能被结构化沉淀
3. 流程、知识、技能三者开始关联
4. 系统能基于岗位或任务推荐模板 / 知识 / 流程
5. 系统能够逐步学习个人工作习惯，并以可编辑、可审计、可回滚的方式辅助执行

### 8.5 Obsidian 生产级整合方案

Obsidian 不是一个“顺手加一下”的外围能力，而应该被定义为：

**Ti Work 的本地 Markdown 知识仓入口之一，用于承接个人知识、团队知识、项目知识与流程产物沉淀。**

整合目标不是做一个“能打开 Obsidian 文件”的小工具，而是让 Ti Work 能把：

- 会话结果
- 研究结论
- 流程执行产物
- 会议纪要
- SOP / FAQ / 模板
- 员工经验与团队规则

持续沉淀到企业可复用的本地知识仓中。

#### 8.5.1 方案结论

生产级方案不建议一开始就做 Obsidian 插件深绑，也不建议把 Vault 当普通文件夹裸暴露给智能体自由写入。

推荐采用三层路线：

1. **P1：受控接入**
   - 先以“受控本地知识仓”接入 Obsidian Vault
   - 技术上优先走 `MCP Filesystem + Ti Work 内置 Obsidian Skill 抽象`
   - 先解决读、搜、写、归档、模板化写入

2. **P2：治理闭环**
   - 加入审计、目录白名单、敏感目录保护、冲突处理、高危写入确认
   - 让 Vault 写入进入企业可控场景

3. **P3：知识资产化**
   - 把 Obsidian 中的 Markdown 知识与 Ti Work 记忆、流程、规则库、员工画像打通
   - 让它不只是“笔记存放地”，而是企业知识资产的一部分

#### 8.5.2 为什么首版不做插件深绑

首版不建议直接做 Obsidian 插件级深度整合，原因如下：

1. 插件方案更依赖 Obsidian 内部 API、版本兼容与插件生命周期
2. 企业交付时更难做权限边界与安全说明
3. 多 Vault、同步盘、附件目录、模板目录差异会让首版复杂度迅速升高
4. 当前 Ti Work 已具备技能生态与 MCP 扩展能力，先走本地知识仓方案更稳、更快、更容易产品化

因此首版应明确坚持：

- **先接 Vault，不先绑 Obsidian App 内部状态**
- **先把知识沉淀闭环打通，不先追求当前打开笔记、Graph View、Backlinks 实时联动**

#### 8.5.3 目标能力边界

Obsidian 整合首个生产级版本必须至少具备以下能力：

1. 读取指定 Vault 内的 Markdown 笔记
2. 按文件名、路径、标签、Frontmatter、正文关键字搜索
3. 在指定目录下新建笔记、追加内容、更新 Frontmatter
4. 将 Ti Work 会话 / 流程 / 研究结果一键沉淀到 Vault
5. 支持模板化输出，如会议纪要、日报、周报、项目纪要、SOP 草稿
6. 支持附件关联策略，但首版先只做“引用已有附件路径”与“受控写入附件目录”
7. 所有写入必须落在白名单目录，禁止默认全 Vault 任意写

首版暂不承诺：

- 当前 Obsidian 正在打开哪篇笔记的实时感知
- Graph / Backlinks / Canvas 的原生能力映射
- 双向实时监听所有外部变更并即时回刷 UI
- 对第三方 Obsidian 插件生态的深兼容

#### 8.5.4 推荐技术架构

推荐架构分为四层：

**A. 配置层**

- 在 Ti Work 设置中新增“Obsidian / 本地知识仓”配置区
- 用户选择一个或多个 Vault 根目录
- 每个 Vault 需配置：
  - Vault 名称
  - 根目录
  - 默认写入目录，如 `Ti Work/`
  - 模板目录，如 `Templates/`
  - 附件目录，如 `Assets/`
  - 是否允许创建新目录
  - 是否允许覆盖已有文件

**B. 执行层**

- 首版使用受限文件系统访问能力，只允许访问选定 Vault
- 在执行层之上增加 Ti Work 自己的 `Obsidian Skill`
- 该 Skill 不直接暴露任意文件写入，而是提供更高层动作：
  - 搜索笔记
  - 读取笔记
  - 新建笔记
  - 追加到笔记
  - 按模板生成笔记
  - 写入会议纪要 / 研究结论 / 流程总结

**C. 索引层**

- 对选定 Vault 建立轻量索引
- 至少抽取：
  - 路径
  - 文件名
  - 修改时间
  - 标签
  - YAML Frontmatter
  - 标题层级
  - 摘要
- 索引要服务知识搜索、相关推荐、流程沉淀与知识去重

**D. 治理层**

- 所有写入要记录审计日志
- 敏感目录必须支持只读
- 高风险写入必须要求用户确认
- 失败时要保留原因与重试建议

#### 8.5.5 产品页面与交互落点

Obsidian 整合不应做成孤立入口，而应落在现有规划的几个域中：

1. **知识域**
   - 增加“本地知识仓”子页
   - 展示已接入 Vault、目录结构、索引状态、模板、最近沉淀记录

2. **会话域**
   - 在会话结果区提供“沉淀到知识仓”动作
   - 支持选择目标 Vault、目录、模板、标签

3. **流程域**
   - 流程结束后可自动输出执行纪要到 Vault
   - 模板流程可绑定固定知识沉淀目录

4. **管理域**
   - 展示知识仓写入审计、失败记录、敏感目录策略、索引健康状态

#### 8.5.6 生产级权限与安全策略

这一部分必须从第一版就设计进去，否则不能进入企业场景。

必须具备：

1. **目录白名单**
   - 智能体只允许访问用户已授权的 Vault 根目录
   - 默认写入目录为 Vault 下的 `Ti Work/` 或管理员指定目录

2. **读写分级**
   - 目录可配置为只读、可追加、可新建、可覆盖
   - `/Templates`、`/Archive`、`/Rules` 等目录允许单独配置权限

3. **敏感路径保护**
   - 如 `.obsidian/`、插件目录、同步配置目录默认禁止写入
   - 系统配置文件不允许被模型直接修改

4. **写入确认机制**
   - 跨目录写入、覆盖已有文件、批量写入、删除等动作需确认

5. **审计留痕**
   - 谁在什么时候让系统写了什么文件、追加了什么内容、修改了什么 Frontmatter，必须可追溯

#### 8.5.7 知识沉淀数据规范

为了让后续知识检索、模板推荐、流程关联真正可用，Obsidian 输出不能是随意 Markdown，必须有统一规范。

建议 Ti Work 写入 Vault 的文档默认采用统一 Frontmatter：

```yaml
---
title: ""
source: "ti-work"
vault: ""
created_by: ""
created_at: ""
workspace: ""
session_id: ""
flow_id: ""
knowledge_type: ""
tags: []
status: "draft"
---
```

首版至少统一以下 `knowledge_type`：

- `meeting_note`
- `research_note`
- `process_summary`
- `sop_draft`
- `daily_report`
- `weekly_report`
- `faq_draft`

#### 8.5.8 与 Ti Work 其它能力的联动方式

Obsidian 整合不能独立存在，必须与现有主线联动：

1. **与会话联动**
   - 会话可将回答、总结、审批结果沉淀为 Markdown

2. **与流程联动**
   - 流程模板可约定输出目录与输出模板

3. **与记忆联动**
   - 高频引用的笔记可转为长期记忆条目
   - 关键记忆也可导出为知识仓文档

4. **与技能联动**
   - 不同岗位技能可绑定不同知识模板

5. **与审计联动**
   - 知识仓所有写入必须进入管理域审计记录

#### 8.5.9 分阶段实施方案

##### A. P1 最小生产版

必须完成：

- 单 Vault 接入
- Vault 路径选择与检测
- 知识仓搜索
- 受控目录写入
- Markdown 模板输出
- 会话结果一键沉淀

完成后用户至少能做到：

- 让 Ti Work 把研究结果写入 Obsidian
- 让 Ti Work 把会议纪要写入 Obsidian
- 让 Ti Work 把重复工作的输出按模板沉淀到 Obsidian

##### B. P2 企业可控版

必须完成：

- 多 Vault 管理
- 目录权限模型
- 敏感路径保护
- 写入审计与失败回放
- 批量写入确认
- 索引重建与健康检查

完成后平台才可以进入企业团队级共享知识场景。

##### C. P3 资产化版本

必须完成：

- Vault 文档与企业知识中心双向关联
- 基于岗位 / 任务 / 流程推荐相关笔记
- SOP / FAQ / 模板从笔记中抽取结构化资产
- 规则库与知识仓关联

完成后 Obsidian 不再只是知识载体，而成为企业知识资产体系的一部分。

#### 8.5.10 验收标准

Obsidian 整合生产级方案完成时，至少要同时满足：

1. 用户可在设置中完成 Vault 接入，无需手工命令配置
2. 智能体只能访问被授权的 Vault 与目录
3. 会话 / 流程结果可稳定沉淀为 Markdown 文档
4. 写入内容具备统一 Frontmatter 与模板结构
5. 敏感路径默认受保护，不能被模型任意改写
6. 所有写入、覆盖、失败都有审计记录
7. 普通员工无需理解 Obsidian 技术细节，也能完成知识沉淀闭环

#### 8.5.11 明确不采用的首版路线

为避免方案发散，首版明确不采用以下路线作为主实现：

- 直接把整个 Vault 作为任意文件系统暴露给模型
- 先做 Obsidian 插件再反向补 Ti Work
- 依赖用户自行安装并配置多个外部脚本后才可使用
- 无模板、无权限、无审计的自由写入方案

结论：

**Ti Work 对 Obsidian 的正确整合方式，不是“再加一个笔记入口”，而是把 Obsidian Vault 作为企业知识沉淀的本地知识仓之一，以受控目录、统一模板、审计留痕和流程联动的方式纳入知识中心体系。**

### 8.6 个人工作画像与习惯学习中心生产级方案

Ti Work 如果要成为“日常熟悉我工作流程”的桌面智能体，不能只停留在开启记忆、保存几条偏好或手工写修正项。

生产级目标应该是：

**让系统以受控、可解释、可编辑、可治理的方式，逐步学习个人的工作目标、常做流程、输出偏好、授权习惯与高频操作模式，并持续提升协作效率。**

这件事本质上不是“训练模型参数”，而是建立一套围绕个人工作的：

- 画像模型
- 习惯学习
- 流程沉淀
- 偏好推荐
- 授权习惯
- 记忆治理

的产品化闭环。

#### 8.6.1 方案结论

当前路线不应走“私有微调模型先行”，而应优先采用：

1. **工作画像 + 长短期记忆**
   - 记录用户稳定偏好、角色、工作域、目录习惯、常用模板、常见规则

2. **历史会话与执行轨迹提炼**
   - 从对话、文件操作、流程执行、审批习惯中提取高频模式

3. **流程模板化与可复用**
   - 把重复工作升级为模板、流程和推荐动作

4. **可视化治理**
   - 所有学习结果可查看、可编辑、可停用、可回滚、可审计

也就是说：

- 首版不追求“模型被重新训练”
- 首版追求“系统越来越懂你的工作方式，并且这个过程用户可控”

#### 8.6.2 它要解决什么问题

这一能力至少要解决以下真实问题：

1. 用户每次都要重复说明自己的工作背景
2. 用户常做的流程无法被系统主动识别和推荐
3. 输出风格、文档结构、常用模板无法稳定复用
4. 目录访问、危险动作确认、授权边界无法体现个人习惯
5. 系统虽然“有记忆”，但用户不知道记住了什么，也无法安心依赖

#### 8.6.3 个人工作画像的数据模型

生产级版本必须有清晰的数据模型，不能把所有信息都混进一份 MEMORY.md。

建议至少拆成六类：

1. **基础身份画像**
   - 姓名 / 角色 / 部门 / 岗位
   - 工作职责
   - 常用系统
   - 常用文档类型

2. **工作偏好画像**
   - 输出语言偏好
   - 文档结构偏好
   - 汇报风格偏好
   - 表格 / Markdown / PPT 等格式偏好

3. **流程画像**
   - 常做任务
   - 高频操作顺序
   - 常用目录
   - 常用网站 / 系统 / 数据源
   - 常用审批链路

4. **授权习惯画像**
   - 哪类动作通常可以直接允许
   - 哪类动作必须先确认
   - 哪类目录始终禁止
   - 哪类风险动作必须进入审批

5. **知识与模板画像**
   - 高频引用知识
   - 常用模板
   - 偏好的 SOP
   - 常见纠正项

6. **关系与上下文画像**
   - 常协作对象
   - 常处理项目
   - 当前阶段重点任务
   - 时间性工作上下文

#### 8.6.4 学习来源与采集边界

系统不能“偷偷学习一切”，而应明确学习来源与边界。

建议学习来源限定为：

1. 用户明确保存的偏好
2. 会话中被确认有效的总结与纠正
3. 已执行成功的流程与模板
4. 用户授权后的操作轨迹
5. 用户主动沉淀的文档、知识仓内容与工作记录

必须明确不默认学习的内容：

- 未确认的临时聊天噪音
- 敏感凭据
- 私密目录中的原始文件内容
- 用户拒绝授权的动作细节
- 与工作画像无关的偶发操作

#### 8.6.5 学习闭环设计

生产级方案不能只有“记住”，必须形成完整闭环：

1. **捕获**
   - 从会话、流程、执行、审批、知识沉淀中收集候选信号

2. **提炼**
   - 把原始行为提炼成偏好、流程片段、模板建议、规则候选

3. **确认**
   - 低风险项可自动纳入候选
   - 中高风险项必须由用户确认后才进入长期画像

4. **应用**
   - 在新会话、工作台、执行页、流程页中主动推荐

5. **修正**
   - 用户可标记“不适用”“不要再这样做”“仅本项目适用”

6. **治理**
   - 支持停用、回滚、删除、审计

#### 8.6.6 产品页面与交互落点

这项能力必须是显式产品能力，而不是藏在设置细节里。

建议页面落点如下：

1. **知识域**
   - 新增“个人工作画像”子页
   - 展示当前画像摘要、偏好、规则、常用模板、常用知识

2. **工作台**
   - 展示“今日建议动作”“高频流程快捷入口”“与你相关的知识与模板”

3. **会话域**
   - 发起任务时注入相关画像上下文
   - 显示“已应用哪些个人偏好 / 模板 / 规则”

4. **流程域**
   - 将高频任务转为个人流程模板
   - 显示“系统识别到你最近重复执行的流程”

5. **设置 / 权限与安全**
   - 展示授权习惯画像
   - 配置哪些学习结果可自动应用，哪些必须确认

#### 8.6.7 生产级推荐能力

当个人工作画像形成后，系统至少要能做四类推荐：

1. **任务推荐**
   - 识别你常做的工作，给出快捷入口

2. **模板推荐**
   - 根据任务类型推荐文档模板、流程模板、知识模板

3. **上下文推荐**
   - 自动带入相关知识、历史会话、近期文件、相关项目资料

4. **授权建议**
   - 根据你的既往授权习惯，预估哪些动作可能需要确认

#### 8.6.7.A 标题驱动的信息搜集与相关性整理

这是个人工作画像与习惯学习中必须重点支持的高频场景之一。

很多真实办公任务里，用户不会一开始就给出完整需求，而只是给一个标题、主题或一句方向描述，例如：

- “整理一下 xx 行业近期动态”
- “帮我看看这个主题有没有值得跟进的资料”
- “按这个标题搜一下，并整理和我要的内容最相关的信息”

这类场景的目标，不是单纯“浏览器搜索”，而是让系统逐步学会用户的信息搜集方式与相关性判断习惯。

生产级版本应把它定义为：

**标题驱动的信息搜集与相关性整理助手。**

至少需要包含以下能力：

1. **标题意图补全**
   - 用户只给标题时，系统先推断潜在目标
   - 自动补全可能需要的关键词、行业上下文、时间范围、比较维度、排除条件
   - 在不确定时给出最少量澄清，而不是让用户重新完整写一遍需求

2. **搜索策略学习**
   - 学习用户常用搜索源
   - 学习用户常用关键词风格、限定词、排除词
   - 学习用户偏好的信息类型，如新闻、研报、官方文档、社区讨论、政策原文

3. **结果相关性分层**
   - 不只是抓取结果列表，而是判断每条信息与当前目标的相关程度
   - 至少分为：
     - 高相关
     - 中相关
     - 低相关
     - 噪音 / 可忽略

4. **结构化整理输出**
   - 按用户习惯输出固定结构，而不是每次自由发挥
   - 输出结构至少支持：
     - 核心结论
     - 关键证据
     - 高相关信息摘要
     - 可进一步跟进的信息
     - 参考来源列表

5. **偏好纠正与持续学习**
   - 用户可标记“这类信息太泛”“这类来源以后少给我”“这类结构正是我想要的”
   - 系统基于用户的保留、删除、采纳、否定行为持续修正排序与整理逻辑

#### 8.6.7.B 与浏览器、知识、流程的联动要求

这项能力不能孤立实现，必须与其它主线联动：

1. **与浏览器自动化联动**
   - 浏览器负责搜索、打开、提取、抓取候选资料

2. **与知识中心联动**
   - 高相关结果可一键沉淀为知识条目、研究笔记或 Obsidian 文档

3. **与流程中心联动**
   - 常见研究动作可沉淀为“信息搜集流程模板”
   - 例如：标题输入 → 搜索 → 筛选 → 相关性排序 → 结构化总结 → 知识沉淀

4. **与个人工作画像联动**
   - 系统要记住你偏好的信息源、输出结构、相关性判断口径

#### 8.6.7.C 分阶段实施要求

##### P1 基础版

- 标题驱动搜索
- 多结果抓取
- 初步相关性排序
- 固定结构摘要输出

##### P2 学习版

- 学习用户常用信息源与筛选习惯
- 学习用户偏好的整理结构
- 支持用户对相关性结果进行纠正反馈

##### P3 生产级版

- 形成稳定的信息搜集画像
- 可解释为什么某条结果被判定为高相关
- 与知识沉淀、流程模板、权限与安全中心完全联动

#### 8.6.7.D 验收标准

这一能力完成时，至少要同时满足：

1. 用户只给标题或主题时，系统也能启动有效的信息搜集流程
2. 系统能对候选结果进行相关性分层，而不是只罗列搜索结果
3. 输出结果能按用户偏好的固定结构整理
4. 用户能够纠正“哪些相关、哪些不相关”，且系统后续会学习这些反馈
5. 高相关内容可进一步沉淀到知识中心或本地知识仓
6. 用户能够明显感受到系统越来越接近自己的信息搜集与整理习惯

#### 8.6.8 记忆治理与质量控制

这是生产级支持的关键，不然只会越用越乱。

至少要具备：

1. **记忆分层**
   - 会话级短期记忆
   - 个人长期记忆
   - 项目级记忆
   - 团队级知识

2. **有效性控制**
   - 过期策略
   - 冲突检测
   - 重复内容合并
   - 低置信度候选不自动升级为长期画像

3. **人工治理**
   - 可编辑
   - 可停用
   - 可删除
   - 可回滚

4. **适用范围**
   - 全局适用
   - 某个项目适用
   - 某个流程适用
   - 某个会话临时适用

#### 8.6.9 与权限与安全中心的联动

个人工作画像不能绕开权限与安全中心。

必须明确：

1. 系统不能因为“学习到你习惯这样做”就自动突破权限边界
2. 授权习惯只能在已允许的策略框架内生效
3. 危险动作永远服从权限与安全中心的规则
4. 用户必须能看到“这次推荐或默认行为，是基于哪条画像 / 规则 / 历史习惯”

#### 8.6.10 与知识中心、流程中心的联动

这项能力必须和已有主线打通：

1. **与知识中心联动**
   - 高频知识引用可进入个人工作画像
   - 画像中的模板偏好可反向影响知识沉淀格式

2. **与流程中心联动**
   - 高频重复操作自动形成流程候选
   - 用户确认后升级为个人流程模板

3. **与会话中心联动**
   - 新会话自动带入相关偏好、项目背景、输出格式习惯

4. **与 Obsidian / 本地知识仓联动**
   - 用户常用知识仓目录、模板、标签、Frontmatter 可进入画像

#### 8.6.11 分阶段实施方案

##### A. P1 基础可用版

必须完成：

- 个人偏好配置
- 用户资料可视化
- 基础长期记忆开关
- 会话中的画像上下文注入
- 常用模板与常用目录的显式配置

完成后，系统至少能做到“知道你是谁、常用什么、偏好什么”。

##### B. P2 学习闭环版

必须完成：

- 高频流程识别
- 授权习惯候选
- 模板推荐
- 候选记忆确认面板
- 记忆治理与审计

完成后，系统至少能做到“开始学习你怎么工作，并且这个过程用户可控”。

##### C. P3 生产级画像版

必须完成：

- 个人工作画像中心
- 长短期记忆分层
- 项目 / 任务 / 流程级适用范围
- 推荐解释能力
- 可编辑 / 可回滚 / 可停用治理

完成后，系统才可以称为“日常熟悉你工作流程的生产级桌面智能体”。

#### 8.6.12 验收标准

个人工作画像与习惯学习中心完成时，至少要同时满足：

1. 系统能稳定保存并应用个人偏好、输出风格、常用模板与常用目录
2. 系统能从高频成功工作中提取流程候选，而不是只保存零散记忆
3. 用户能清楚看到系统学到了什么，并可编辑、停用、删除、回滚
4. 所有长期画像都具备来源说明、适用范围与更新时间
5. 画像推荐不会绕开权限与安全中心
6. 会话、流程、知识、授权习惯之间能形成联动闭环
7. 用户能够明显感受到“系统越来越懂我的工作方式”，且不会产生失控感

#### 8.6.13 明确不采用的方案

首版明确不采用以下路线：

- 直接把“记忆开关”当作生产级习惯学习能力
- 用不可解释的自动学习替代用户确认
- 将所有偏好、流程、规则混写在单一 Markdown 中长期堆积
- 在没有治理、回滚、审计前就默认自动应用高风险习惯
- 把“熟悉你的工作方式”理解成必须先做模型微调

结论：

**Ti Work 要实现“熟悉你日常工作流程”的生产级能力，核心不是先训练模型参数，而是先建设个人工作画像与习惯学习中心，让系统在可视化、可确认、可治理的前提下，持续学习你的任务模式、输出偏好、流程习惯与授权边界。**

## 9. P4：自修复与自进化

### 9.1 阶段目标

让平台具备“越用越稳定、越用越懂组织”的能力。

### 9.2 本阶段要完成的能力

#### A. 自修复

必须形成：

- 工具失败分类
- 失败诊断
- 自动重试策略
- 修复建议
- 回滚建议

用户效果：

- 系统不只报错，还能解释、建议、辅助恢复

#### B. 自进化

必须形成：

- 基于企业知识与员工行为的模板优化
- 高频工作自动总结
- 低效流程识别
- 模板与规则持续升级

用户效果：

- 平台逐步具备组织学习能力

### 9.3 P4 交付物

- 执行失败诊断中心
- 修复策略中心
- 模板 / 规则优化推荐
- 组织经验增量沉淀机制

### 9.4 P4 完成标准

必须同时满足：

1. 常见失败能够自动诊断并给出下一步
2. 高频流程可得到持续优化
3. 企业知识、流程、模板、岗位画像形成自增强关系

## 10. 阶段依赖关系

```
P0 Hermes 底座稳定
  ↓
P1 企业办公核心闭环
  ↓
P2 数据与审计闭环
  ↓
P3 企业知识与员工技能沉淀
  ↓
P4 自修复与自进化
```

解释：

- 没有 P0，就没有可靠执行底座
- 没有 P1，就没有真实办公入口
- 没有 P2，就无法进入企业受控场景
- 没有 P3，就无法形成组织资产
- 没有 P4，就谈不上长期自增长

## 11. 每阶段验收问法

后续每阶段评审都必须回答四个问题：

1. 这阶段到底新增了哪些页面和能力？
2. 用户能完成什么新的真实工作？
3. 哪些数据 / 知识 / 规则开始被沉淀？
4. 什么证据证明阶段已经完成？

如果回答不清，就说明阶段定义还不够具体，不能进入开发。

## 13. 结论

Ti Work 的正确方向不是“再堆更多功能页”，而是按下面这条主线推进：

**先把安装版执行底座打稳，让用户安装成功后就能对话，再把工作入口收口，再把文件 / 浏览器 / 流程 / 数据 / 知识打成闭环，最后让平台具备企业级沉淀、自修复与自进化能力。**

# Ti Work 企业日常办公平台规划

> 状态：实施规划文档（2026-08-15 更新）
> 适用范围：Ti Work 桌面端后续产品规划、研发排期、页面收口、验收标准
> 当前最高优先级：**P0 免安装版链路已打通，下一步必须完成安装版内置 Hermes 网关闭环，确保用户安装成功后即可进入可对话状态**

---

## 1. 产品重新定义

Ti Work 后续不是继续做“功能很多的 AI 桌面工具”，而是做一套面向企业员工真实日常工作的桌面办公平台。

目标形态：

- 员工可以用它处理文件、网页系统、知识库、流程任务、数据库、日常文档与表格类工作
- 平台可以沉淀企业知识、团队经验、岗位 SOP、员工技能与常见执行模板
- 平台可以把“单次会话”升级成“可复用的业务执行能力”
- 平台逐步具备自修复、自优化、自进化能力

一句话定义：

**Ti Work = 企业员工的 AI 办公操作台 + 企业知识 / 流程 / 技能沉淀平台。**

---

## 2. 当前问题

当前产品不是能力绝对不足，而是存在三个核心问题：

1. **安装版尚未闭环**：免安装验证已通过，但正式安装版还没有做到“安装阶段就把 Hermes 网关准备好，安装后首启即可对话”
2. **能力太散**：左侧一级菜单过多，用户无法快速识别主路径
3. **缺少闭环**：文件、浏览器、记忆、数据库、流程、审计还没有串成企业办公闭环

因此后续路线必须先做：

- 底座稳定
- 菜单收口
- 核心工作闭环
- 组织沉淀闭环

---

## 3. 左侧菜单目标结构

当前侧边栏入口太多，开发者视角过重。后续要收敛为 6 个一级核心域，底部保留设置和帮助。

### 3.1 目标一级菜单

| 菜单 | 核心定位 | 主要承载内容 |
|---|---|---|
| 工作台 | 今日工作入口 | 今日待办、提醒、最近流程、最近文件、工作摘要 |
| 会话 | AI 任务发起中心 | 会话、附件、审批提醒、会话历史 |
| 执行 | 真正做事的地方 | 文件、浏览器自动化、终端、数据库操作 |
| 流程 | 可复用执行能力 | 任务、编排、多智能体、定时任务、流程模板 |
| 知识 | 企业与个人沉淀 | 记忆、技能、用户档案、企业知识、规则库 |
| 管理 | 运营与治理 | 分析、审计、日志、运维、权限、健康检查 |

底部固定：

- 设置
- 帮助 / 文档

### 3.2 当前菜单映射

| 当前入口 | 未来归属 |
|---|---|
| 工作台 | 工作台 |
| 会话 / 会话历史 | 会话 |
| 文件 / 终端 | 执行 |
| 任务 / 任务编排 / 多智能体 / 待办 / 定时任务 | 流程 |
| 记忆 / 技能 / 用户档案 / 模式与纠正 | 知识 |
| 分析 / 血缘 / 审计记录 / 日志 / 运维视图 | 管理 |

### 3.3 菜单收口原则

- 不再继续新增一级菜单
- 实验能力默认不进入一级导航
- 二级功能放入域页面内部 tab / 面板
- 先按“用户工作任务”组织，不按“技术模块”组织

---

## 4. 总实施路线

产品按 `P0 -> P1 -> P2 -> P3 -> P4` 推进，每个阶段都要有明确产物、功能边界与验收标准。

---

## 5. P0：Hermes 首装与执行底座稳定

### 5.0 当前状态

P0 已完成第一阶段闭环：

- 免安装版 / `win-unpacked` 已可自动拉起 Hermes 网关
- `8642` 健康检查可通过
- 模型列表可正常返回
- 首条消息已可真实发送并收到回复

但对正式交付来说，P0 还差最后一个必须完成的版本：

- **安装版闭环**

也就是：用户在安装 Ti Work 的过程中，就已经把 Hermes 网关相关依赖、运行目录、配置骨架一并准备好；安装成功后首次打开应用，要么直接可对话，要么明确提示配置 API Key，配置完成后立即可对话。

### 5.1 阶段目标

让桌面端正式安装版真正达到：

- 安装过程中就完成 Hermes 网关所需资源与目录准备
- 用户安装成功后第一次打开即可进入可用状态，而不是再经历长时间自举等待
- 若未配置模型 API Key，首启必须给出清晰、唯一、可完成的配置引导
- 用户完成 API Key 配置后，可立即稳定完成第一条消息

### 5.2 本阶段必须完成的功能

1. **安装版后端稳定启动**
   - 不依赖用户机器外部 `node.exe`
   - 使用安装包自身 runtime 拉起本地后端

2. **安装过程中完成 Hermes 预装**
   - 安装包内置 Hermes 固定版本资源
   - 安装程序在安装阶段完成 Hermes 工作目录准备
   - 安装程序在安装阶段完成 gateway 所需依赖与运行时初始化
   - 安装结束时，本地已具备可启动 Hermes 网关的最小完整环境

3. **首启即用 / 首启即配**
   - 若本地已有有效模型配置，首次打开应用即可直接对话
   - 若缺少 API Key，不允许只给模糊报错，必须进入明确配置引导
   - 配置页只保留完成对话所需最小必要项：provider / model / baseUrl / apiKey
   - API Key 保存成功后，无需手工重启整套链路即可开始对话

4. **安装状态和失败原因可表达**
   - 安装阶段失败时要明确告诉用户是哪个安装步骤失败
   - 首启阶段失败时要能区分：网关未启动、模型未配置、配置无效
   - 禁止再出现“网关已启动但实际不可对话”的假成功状态

5. **路径与版本策略固定**
   - 严禁安装阶段回退到在线拉取 Hermes 源码
   - 严禁依赖用户本机 Git / Node 外部环境
   - 安装版与免安装验证版必须使用同一套固定版本 Hermes 资源策略

### 5.3 页面 / 交互结果

- 安装过程中：
  - 若 Hermes 预装仍在进行，安装器内必须有明确进度或步骤提示
  - 不允许把 Hermes 安装问题全部留到用户首次打开应用后再处理
- 首次打开应用后：
  - 能直接进入工作界面
  - 若网关已就绪且模型已配置，可直接对话
  - 若缺少模型 API Key，显示清晰配置引导，而不是离线报错
- 用户配置 API Key 后：
  - 无需手工执行命令
  - 无需理解 Hermes 细节
  - 回到会话页即可正常发送消息

### 5.4 完成标准

必须同时满足：

1. 安装版安装完成后，本地 Hermes 网关运行环境已准备完毕
2. 首次打开 `Ti Work.exe` 时，不再依赖长时间首装 bootstrap 才能进入可用状态
3. 若模型配置已存在，用户首次进入会话页即可直接成功发送一条消息
4. 若模型配置不存在，系统必须明确提示配置 API Key，且配置成功后立即可发送第一条消息
5. 用户全程无需手工执行任何命令
6. 不再出现误导性的“执行引擎未连接”或“网关失败”假报错

### 5.5 安装版实施重点

这一阶段的核心不是继续优化免安装体验，而是把正式安装流程做成真正的产品闭环。

#### A. 安装程序要负责什么

- 选择安装路径
- 写入 Ti Work 应用主体
- 写入 Hermes 固定版本资源
- 完成 Hermes 工作目录初始化
- 生成网关最小配置骨架
- 预置运行所需 token / env / config 骨架
- 完成必要依赖准备与网关可启动性检查

#### B. 首次启动要负责什么

- 检查 Hermes 网关是否可直接启动
- 检查本地模型配置是否完整
- 若缺少 API Key，则进入配置引导，而不是报错
- 若配置完整，则直接进入可对话状态

#### C. 用户体验目标

- 用户理解的是“安装 Ti Work”，而不是“再安装一个 Hermes”
- 用户不需要知道 Hermes 工作目录、bootstrap、manifest、gateway 这些技术概念
- 对用户来说，安装成功的标准就是：打开后能开始对话；若缺 Key，就把 Key 配完后立刻能对话

### 5.6 未完成前禁止推进的内容

- 浏览器自动化主卖点
- 数据库产品化
- 移动端主路径
- 企业能力对外宣发
- 一级菜单继续扩张

## 6. P1：企业办公核心闭环

### 6.1 阶段目标

让 Ti Work 从“能聊天”升级为“能处理员工日常工作”。

P1 解决的是：员工每天打开软件，到底能拿它完成什么具体工作。

### 6.2 本阶段要形成的产品能力

#### A. 工作台

必须形成一个真正的“今日工作入口”页面，至少包含：

- 今日待办
- 最近文件
- 最近会话
- 最近流程
- 工作提醒 / 审批提醒
- 今日工作摘要

用户效果：

- 打开软件第一眼就知道今天要做什么
- 不需要先理解系统结构，再决定去哪个页面

#### B. 会话中心

会话页要从普通对话框升级为“任务发起中心”：

- 支持从文件、流程、网页任务发起会话
- 支持结构化任务上下文
- 支持附件、指令模板、会话标签
- 支持历史回溯

用户效果：

- 会话不只是聊天，而是办公任务的入口

#### C. 执行中心

执行域至少要覆盖四件事：

1. 文件处理
2. 浏览器自动化
3. 终端执行
4. 数据库操作入口（先做基础版）

用户效果：

- 用户不是只能“问 AI”，而是可以让它真正做事

#### D. 流程中心

把离散能力转成可复用流程：

- 任务
- 编排
- 多智能体
- 定时任务
- 流程模板

用户效果：

- 重复工作不再一遍遍重新描述
- 常见工作可以保存成模板

#### E. 知识中心

先形成“个人+团队基础沉淀”：

- 记忆
- 技能
- 用户档案
- 规则 / 纠正项

用户效果：

- 平台开始记住企业和员工怎么工作

### 6.3 P1 交付物

必须至少形成：

- 新一级菜单结构原型
- 工作台页面 v1
- 执行中心页面 v1
- 流程中心页面 v1
- 知识中心页面 v1
- 会话作为任务发起中心的交互收口

### 6.4 P1 完成标准

必须同时满足：

1. 一个普通企业员工无需懂技术，也能看懂主菜单
2. 用户能完成至少 3 类真实办公闭环：
   - 文件整理 / 改写 / 汇总
   - 网页系统查询 / 填报 / 提取
   - 重复工作保存为流程模板
3. 不必在十几个菜单之间来回找功能

### 6.5 P1 不做什么

- 先不追求复杂企业中台
- 先不做极重的数据库治理
- 先不做大规模组织分析能力

## 7. P2：数据与审计闭环

### 7.1 阶段目标

让平台从“个人好用”升级到“组织可放心使用”。

P2 关注的是：执行行为必须留痕、可审计、可恢复、可治理。

### 7.2 本阶段要完成的能力

#### A. 数据库操作工作台

必须具备：

- 数据库连接配置
- 常用查询模板
- 查询结果表格化展示
- 导出结果
- 高危 SQL 限制或审批

用户效果：

- 业务和运营人员能在受控范围内做常见数据工作

#### B. 审计与回放

必须形成：

- 文件操作审计
- 浏览器操作审计
- 数据库操作审计
- 流程执行记录
- 失败记录与原因展示

用户效果：

- 任何重要动作都能追溯
- 领导、管理员、操作者都知道发生过什么

#### C. 权限与高危动作门禁

必须形成：

- 高危动作审批
- 敏感目录 / 敏感库限制
- 执行风险标记
- 受控重试

用户效果：

- 平台可进入企业真实工作场景，而不是停留在个人玩具层面

### 7.3 P2 交付物

- 数据库操作页 v1
- 审计中心 v1
- 执行回放记录页 v1
- 高危动作审批规则 v1
- 执行结果导出 / 留痕能力

### 7.4 P2 完成标准

必须同时满足：

1. 文件 / 浏览器 / 数据库 / 流程执行均可留痕
2. 管理者可以查到谁做了什么
3. 高风险动作具备审批或限制机制
4. 用户能查看失败原因和执行历史

## 8. P3：企业知识与员工技能沉淀

### 8.1 阶段目标

让平台不只是“执行工具”，而是开始变成企业知识资产平台。

### 8.2 本阶段要完成的能力

#### A. 企业知识库

沉淀内容包括：

- 制度文档
- 岗位 SOP
- 业务 FAQ
- 项目经验
- 会议结论
- 模板文件
- 本地知识仓（含 Obsidian Vault）

用户效果：

- 新人能快速检索并复用组织经验

#### B. 员工技能画像

要沉淀：

- 岗位角色
- 常做任务
- 擅长流程
- 常用模板
- 权限边界
- 操作偏好

用户效果：

- 系统逐步知道不同员工最适合怎样协作

#### C. 团队规则与纠错库

必须形成：

- 企业常见错误集
- 修正建议
- 最佳实践
- 模板推荐规则

用户效果：

- 经验开始从“人脑中的经验”变成“组织可复用资产”

### 8.3 P3 交付物

- 企业知识中心 v1
- Obsidian 知识仓整合 v1
- 岗位 / 员工画像模型 v1
- 团队规则库 v1
- 模板推荐机制 v1

### 8.4 P3 完成标准

必须同时满足：

1. 新人能依赖系统快速找到企业知识
2. 老员工的经验能被结构化沉淀
3. 流程、知识、技能三者开始关联
4. 系统能基于岗位或任务推荐模板 / 知识 / 流程

### 8.5 Obsidian 生产级整合方案

Obsidian 不是一个“顺手加一下”的外围能力，而应该被定义为：

**Ti Work 的本地 Markdown 知识仓入口之一，用于承接个人知识、团队知识、项目知识与流程产物沉淀。**

整合目标不是做一个“能打开 Obsidian 文件”的小工具，而是让 Ti Work 能把：

- 会话结果
- 研究结论
- 流程执行产物
- 会议纪要
- SOP / FAQ / 模板
- 员工经验与团队规则

持续沉淀到企业可复用的本地知识仓中。

#### 8.5.1 方案结论

生产级方案不建议一开始就做 Obsidian 插件深绑，也不建议把 Vault 当普通文件夹裸暴露给智能体自由写入。

推荐采用三层路线：

1. **P1：受控接入**
   - 先以“受控本地知识仓”接入 Obsidian Vault
   - 技术上优先走 `MCP Filesystem + Ti Work 内置 Obsidian Skill 抽象`
   - 先解决读、搜、写、归档、模板化写入

2. **P2：治理闭环**
   - 加入审计、目录白名单、敏感目录保护、冲突处理、高危写入确认
   - 让 Vault 写入进入企业可控场景

3. **P3：知识资产化**
   - 把 Obsidian 中的 Markdown 知识与 Ti Work 记忆、流程、规则库、员工画像打通
   - 让它不只是“笔记存放地”，而是企业知识资产的一部分

#### 8.5.2 为什么首版不做插件深绑

首版不建议直接做 Obsidian 插件级深度整合，原因如下：

1. 插件方案更依赖 Obsidian 内部 API、版本兼容与插件生命周期
2. 企业交付时更难做权限边界与安全说明
3. 多 Vault、同步盘、附件目录、模板目录差异会让首版复杂度迅速升高
4. 当前 Ti Work 已具备技能生态与 MCP 扩展能力，先走本地知识仓方案更稳、更快、更容易产品化

因此首版应明确坚持：

- **先接 Vault，不先绑 Obsidian App 内部状态**
- **先把知识沉淀闭环打通，不先追求当前打开笔记、Graph View、Backlinks 实时联动**

#### 8.5.3 目标能力边界

Obsidian 整合首个生产级版本必须至少具备以下能力：

1. 读取指定 Vault 内的 Markdown 笔记
2. 按文件名、路径、标签、Frontmatter、正文关键字搜索
3. 在指定目录下新建笔记、追加内容、更新 Frontmatter
4. 将 Ti Work 会话 / 流程 / 研究结果一键沉淀到 Vault
5. 支持模板化输出，如会议纪要、日报、周报、项目纪要、SOP 草稿
6. 支持附件关联策略，但首版先只做“引用已有附件路径”与“受控写入附件目录”
7. 所有写入必须落在白名单目录，禁止默认全 Vault 任意写

首版暂不承诺：

- 当前 Obsidian 正在打开哪篇笔记的实时感知
- Graph / Backlinks / Canvas 的原生能力映射
- 双向实时监听所有外部变更并即时回刷 UI
- 对第三方 Obsidian 插件生态的深兼容

#### 8.5.4 推荐技术架构

推荐架构分为四层：

**A. 配置层**

- 在 Ti Work 设置中新增“Obsidian / 本地知识仓”配置区
- 用户选择一个或多个 Vault 根目录
- 每个 Vault 需配置：
  - Vault 名称
  - 根目录
  - 默认写入目录，如 `Ti Work/`
  - 模板目录，如 `Templates/`
  - 附件目录，如 `Assets/`
  - 是否允许创建新目录
  - 是否允许覆盖已有文件

**B. 执行层**

- 首版使用受限文件系统访问能力，只允许访问选定 Vault
- 在执行层之上增加 Ti Work 自己的 `Obsidian Skill`
- 该 Skill 不直接暴露任意文件写入，而是提供更高层动作：
  - 搜索笔记
  - 读取笔记
  - 新建笔记
  - 追加到笔记
  - 按模板生成笔记
  - 写入会议纪要 / 研究结论 / 流程总结

**C. 索引层**

- 对选定 Vault 建立轻量索引
- 至少抽取：
  - 路径
  - 文件名
  - 修改时间
  - 标签
  - YAML Frontmatter
  - 标题层级
  - 摘要
- 索引要服务知识搜索、相关推荐、流程沉淀与知识去重

**D. 治理层**

- 所有写入要记录审计日志
- 敏感目录必须支持只读
- 高风险写入必须要求用户确认
- 失败时要保留原因与重试建议

#### 8.5.5 产品页面与交互落点

Obsidian 整合不应做成孤立入口，而应落在现有规划的几个域中：

1. **知识域**
   - 增加“本地知识仓”子页
   - 展示已接入 Vault、目录结构、索引状态、模板、最近沉淀记录

2. **会话域**
   - 在会话结果区提供“沉淀到知识仓”动作
   - 支持选择目标 Vault、目录、模板、标签

3. **流程域**
   - 流程结束后可自动输出执行纪要到 Vault
   - 模板流程可绑定固定知识沉淀目录

4. **管理域**
   - 展示知识仓写入审计、失败记录、敏感目录策略、索引健康状态

#### 8.5.6 生产级权限与安全策略

这一部分必须从第一版就设计进去，否则不能进入企业场景。

必须具备：

1. **目录白名单**
   - 智能体只允许访问用户已授权的 Vault 根目录
   - 默认写入目录为 Vault 下的 `Ti Work/` 或管理员指定目录

2. **读写分级**
   - 目录可配置为只读、可追加、可新建、可覆盖
   - `/Templates`、`/Archive`、`/Rules` 等目录允许单独配置权限

3. **敏感路径保护**
   - 如 `.obsidian/`、插件目录、同步配置目录默认禁止写入
   - 系统配置文件不允许被模型直接修改

4. **写入确认机制**
   - 跨目录写入、覆盖已有文件、批量写入、删除等动作需确认

5. **审计留痕**
   - 谁在什么时候让系统写了什么文件、追加了什么内容、修改了什么 Frontmatter，必须可追溯

#### 8.5.7 知识沉淀数据规范

为了让后续知识检索、模板推荐、流程关联真正可用，Obsidian 输出不能是随意 Markdown，必须有统一规范。

建议 Ti Work 写入 Vault 的文档默认采用统一 Frontmatter：

```yaml
---
title: ""
source: "ti-work"
vault: ""
created_by: ""
created_at: ""
workspace: ""
session_id: ""
flow_id: ""
knowledge_type: ""
tags: []
status: "draft"
---
```

首版至少统一以下 `knowledge_type`：

- `meeting_note`
- `research_note`
- `process_summary`
- `sop_draft`
- `daily_report`
- `weekly_report`
- `faq_draft`

#### 8.5.8 与 Ti Work 其它能力的联动方式

Obsidian 整合不能独立存在，必须与现有主线联动：

1. **与会话联动**
   - 会话可将回答、总结、审批结果沉淀为 Markdown

2. **与流程联动**
   - 流程模板可约定输出目录与输出模板

3. **与记忆联动**
   - 高频引用的笔记可转为长期记忆条目
   - 关键记忆也可导出为知识仓文档

4. **与技能联动**
   - 不同岗位技能可绑定不同知识模板

5. **与审计联动**
   - 知识仓所有写入必须进入管理域审计记录

#### 8.5.9 分阶段实施方案

##### A. P1 最小生产版

必须完成：

- 单 Vault 接入
- Vault 路径选择与检测
- 知识仓搜索
- 受控目录写入
- Markdown 模板输出
- 会话结果一键沉淀

完成后用户至少能做到：

- 让 Ti Work 把研究结果写入 Obsidian
- 让 Ti Work 把会议纪要写入 Obsidian
- 让 Ti Work 把重复工作的输出按模板沉淀到 Obsidian

##### B. P2 企业可控版

必须完成：

- 多 Vault 管理
- 目录权限模型
- 敏感路径保护
- 写入审计与失败回放
- 批量写入确认
- 索引重建与健康检查

完成后平台才可以进入企业团队级共享知识场景。

##### C. P3 资产化版本

必须完成：

- Vault 文档与企业知识中心双向关联
- 基于岗位 / 任务 / 流程推荐相关笔记
- SOP / FAQ / 模板从笔记中抽取结构化资产
- 规则库与知识仓关联

完成后 Obsidian 不再只是知识载体，而成为企业知识资产体系的一部分。

#### 8.5.10 验收标准

Obsidian 整合生产级方案完成时，至少要同时满足：

1. 用户可在设置中完成 Vault 接入，无需手工命令配置
2. 智能体只能访问被授权的 Vault 与目录
3. 会话 / 流程结果可稳定沉淀为 Markdown 文档
4. 写入内容具备统一 Frontmatter 与模板结构
5. 敏感路径默认受保护，不能被模型任意改写
6. 所有写入、覆盖、失败都有审计记录
7. 普通员工无需理解 Obsidian 技术细节，也能完成知识沉淀闭环

#### 8.5.11 明确不采用的首版路线

为避免方案发散，首版明确不采用以下路线作为主实现：

- 直接把整个 Vault 作为任意文件系统暴露给模型
- 先做 Obsidian 插件再反向补 Ti Work
- 依赖用户自行安装并配置多个外部脚本后才可使用
- 无模板、无权限、无审计的自由写入方案

结论：

**Ti Work 对 Obsidian 的正确整合方式，不是“再加一个笔记入口”，而是把 Obsidian Vault 作为企业知识沉淀的本地知识仓之一，以受控目录、统一模板、审计留痕和流程联动的方式纳入知识中心体系。**

## 9. P4：自修复与自进化

### 9.1 阶段目标

让平台具备“越用越稳定、越用越懂组织”的能力。

### 9.2 本阶段要完成的能力

#### A. 自修复

必须形成：

- 工具失败分类
- 失败诊断
- 自动重试策略
- 修复建议
- 回滚建议

用户效果：

- 系统不只报错，还能解释、建议、辅助恢复

#### B. 自进化

必须形成：

- 基于企业知识与员工行为的模板优化
- 高频工作自动总结
- 低效流程识别
- 模板与规则持续升级

用户效果：

- 平台逐步具备组织学习能力

### 9.3 P4 交付物

- 执行失败诊断中心
- 修复策略中心
- 模板 / 规则优化推荐
- 组织经验增量沉淀机制

### 9.4 P4 完成标准

必须同时满足：

1. 常见失败能够自动诊断并给出下一步
2. 高频流程可得到持续优化
3. 企业知识、流程、模板、岗位画像形成自增强关系

## 10. 阶段依赖关系

```
P0 Hermes 底座稳定
  ↓
P1 企业办公核心闭环
  ↓
P2 数据与审计闭环
  ↓
P3 企业知识与员工技能沉淀
  ↓
P4 自修复与自进化
```

解释：

- 没有 P0，就没有可靠执行底座
- 没有 P1，就没有真实办公入口
- 没有 P2，就无法进入企业受控场景
- 没有 P3，就无法形成组织资产
- 没有 P4，就谈不上长期自增长

## 11. 每阶段验收问法

后续每阶段评审都必须回答四个问题：

1. 这阶段到底新增了哪些页面和能力？
2. 用户能完成什么新的真实工作？
3. 哪些数据 / 知识 / 规则开始被沉淀？
4. 什么证据证明阶段已经完成？

如果回答不清，就说明阶段定义还不够具体，不能进入开发。

## 13. 结论

Ti Work 的正确方向不是“再堆更多功能页”，而是按下面这条主线推进：

**先把安装版执行底座打稳，让用户安装成功后就能对话，再把工作入口收口，再把文件 / 浏览器 / 流程 / 数据 / 知识打成闭环，最后让平台具备企业级沉淀、自修复与自进化能力。**

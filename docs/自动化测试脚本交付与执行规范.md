# 自动化测试脚本交付与执行规范（全链路）

> 适用端：Web / 小程序 / H5 / App / 后端接口
> 参与角色：开发人员、云端仓库、测试机（本地 Windows 专机 / 云端 Linux）
> 核心原则：**一个 commit = 一套业务代码 + 一套对应测试脚本**，版本永远对齐。

---

## 1. 总体流程（时序图）

```
【开发人员】
  1. 改业务代码
  2. AI 基于 git diff 生成改动说明（docs/changelogs/，模板见 docs/templates/改动说明模板.md）
  3. 按本规范 + 改动说明，编写/AI 生成对应测试脚本（test/ 目录）
  4. 本地跑一遍，确认全部通过
  5. git commit（业务代码 + 改动说明 + 测试脚本同 commit）
  6. git push

【云端仓库】
  7. 收到 push（业务代码 + 改动说明 + 测试脚本，同一 commit）

【测试机】
  8. git pull（拉最新 commit）
  9. 安装依赖（lock 文件，固定版本）
  10. 重置测试环境（重建数据库 / 清缓存 / 清理测试数据）
  11. 读改动说明「影响模块」→ 按执行策略跑测试（增量 test:changed / 全量 test:full）
  12. 产出 test-result.json（统一格式，见第 7 章）
  13. 调用报告发布脚本 → 入库 + 通知

【结果反馈】
  14. 结果反馈给开发 → 通过则合入；失败则修复 → 再 push → 回到第 7 步
```

## 2. 测试脚本目录规范（强制）

所有测试脚本放在业务仓库根目录的 `test/` 下，与业务代码同仓同版本。

```
<业务仓库>/
├─ test/
│  ├─ e2e/                        # 端到端 UI 测试
│  │  ├─ web/                     #   Web 端（Playwright 等）
│  │  ├─ miniapp/                 #   小程序（miniprogram-automator 等）
│  │  └─ h5/                      #   H5 端
│  ├─ api/                        # 接口/契约测试
│  ├─ unit/                       # 单元测试
│  ├─ fixtures/                   # 测试数据与夹具（造数脚本、mock 数据）
│  ├─ config/                     # 测试环境配置（不入库敏感信息）
│  │  ├─ env.test.example         #   配置模板（提交）
│  │  └─ env.test                 #   实际配置（gitignore，不提交）
│  ├─ utils/                      # 测试公共工具（登录、造数、清理、断言封装）
│  └─ reporters/                  # 输出适配器（生成 test-result.json）
├─ package.json                   # 统一 test 命令入口（见第 5 章）
└─ jest.config.js / playwright.config.ts / ...
```

约束：

| 编号 | 规则 |
|------|------|
| S-0201 | 测试脚本必须与业务代码同仓，禁止独立测试仓库导致版本错位 |
| S-0202 | 按端、按类型分目录，禁止全部堆在根目录 |
| S-0203 | `fixtures/` 中的测试数据必须可重建、可清理 |
| S-0204 | `config/env.test` 含密钥的配置必须 gitignore，只提交 `env.test.example` 模板 |

## 3. 脚本文件与用例命名规范（强制）

### 3.1 文件命名

```
格式：<模块>_<功能>_<场景>.test.ts
示例：auth_login_failed.test.ts
      order_payment_timeout.test.ts
      generation_copy_result.test.ts
```

### 3.2 用例命名

```
格式：模块_功能_场景_预期
示例：登录_密码错误_提示文案正确
     订单_重复支付_不重复扣款
```

### 3.3 元素定位规范

| 编号 | 规则 |
|------|------|
| S-0301 | UI 自动化必须使用稳定标记定位（`data-testid` / `data-test`），禁止依赖易变的中文文案定位 |
| S-0302 | 元素标记命名：`<page>_<module>_<element>`，如 `order_create_pay_btn` |
| S-0303 | 禁止在测试中硬编码易变文本（如动态倒计时、随机订单号），需通过占位/正则/接口获取 |

### 3.4 用例结构（强制四段）

```
每一条用例必须包含：
  1. 前置条件（beforeAll/beforeEach）：数据构造、登录态
  2. 操作步骤（step 注释）
  3. 断言（expect，必须有具体预期值）
  4. 清理（afterEach/afterAll）：删除测试数据、退出登录态
```

### 3.5 测试数据规范

| 编号 | 规则 |
|------|------|
| S-0305 | 测试数据必须在用例内自建、自清理，禁止依赖共享/生产数据 |
| S-0306 | 测试账号统一由 fixtures 生成，命名带测试标记（如 `test_<runId>@xx.com`） |
| S-0307 | 用例间禁止互相依赖执行顺序，每条可独立运行 |

## 4. 开发侧交付规范（每个 commit 必须满足）

> 注（本项目本地化 TDD 纪律）：当前阶段暂不 git push，但以下交付规范仍须在本地工作区逐条落实——每完成一个功能必须同步产出「改动说明 + 测试脚本」并本地跑通，以 TDD 方式保证代码 / 改动说明 / 测试脚本三者同版本对齐。改动说明生成见第 5 章，脚本撰写参考第 13 章样板。

| 编号 | 交付项 | 要求 |
|------|--------|------|
| S-0401 | 新增功能 | 必须新增对应测试脚本 |
| S-0402 | 修改功能 | 必须更新受影响模块的测试脚本 |
| S-0403 | 删除功能 | 必须同步删除对应测试脚本 |
| S-0404 | 本地验证 | push 前必须本地跑一遍相关模块测试，全部通过 |
| S-0405 | 同 commit | 业务代码与测试脚本必须在**同一个 commit** 提交 |
| S-0406 | 提交信息 | commit message 必须标注测试情况，如 `feat(order): 支付超时处理 + 测试` |

本地验证命令（开发侧必跑）：

```bash
# 跑本次修改相关模块（快）
npm run test:module -- auth

# 跑全量单元+接口（可选，重但保险）
npm run test:unit && npm run test:api
```

## 5. 改动说明与增量测试衔接（强制）

> 每次开发的"改了哪些功能、影响哪些模块"必须以**标准格式改动说明文件**沉淀，既供 AI 生成测试脚本，也供测试机判定增量测试范围。

### 5.1 改动说明文件规范

| 编号 | 规则 |
|------|------|
| S-0501 | 每个 commit 必须附带一份改动说明，由 AI 基于 git diff 按 `docs/templates/改动说明模板.md` 生成 |
| S-0502 | 保存位置：`docs/changelogs/YYYY-MM-DD-<功能短名>.md`，随代码**同 commit** 提交 |
| S-0503 | 必填字段：功能改动点、涉及文件、影响模块；可选字段：测试要点、风险点 |
| S-0504 | AI 生成测试脚本时，必须引用改动说明**文件路径**，禁止用口头/粘贴描述代替 |

### 5.2 增量测试的判定依据

| 编号 | 规则 |
|------|------|
| S-0505 | `npm run test:changed` 以最新 commit 的改动说明「影响模块」作为用例筛选条件 |
| S-0506 | 「影响模块」与测试脚本的映射：模块名对应 `test/` 下 suite 名或 `@module` 标签，映射表维护在 `test/config/` |
| S-0507 | 改动说明「测试要点」中开发者补充的边界/异常场景，必须包含在增量用例中，禁止遗漏 |

### 5.3 与报告发布脚本衔接

`publish-test-report.sh` 的字段来源更新为：

| 报告字段 | 来源 |
|---------|------|
| `updatedFunctions` | 改动说明「功能改动点」 |
| `testedFunctions` | 增量/全量测试实际跑到的 suite 去重 |

### 5.4 流程示意

```
开发完成
  ├─ AI 基于 git diff 生成改动说明 → docs/changelogs/xxx.md（同 commit）
  ├─ AI 依据改动说明 + 总纲 + 本规范 生成测试脚本
  ├─ 本地跑 → 通过 → commit + push
  └─ 测试机 pull → 读改动说明「影响模块」 → 跑 test:changed（增量，每轮 push）
       └─ 发版前 → 跑 test:full（全量回归）
```

## 6. 执行命令规范（测试机统一入口）

`package.json` 统一约定以下命令（测试机直接调用，不感知细节）：

| 命令 | 含义 | 输出 |
|------|------|------|
| `npm run test:unit` | 单元测试 | test-result.json |
| `npm run test:api` | 接口测试 | test-result.json |
| `npm run test:e2e:web` | Web 端 E2E | test-result.json |
| `npm run test:e2e:miniapp` | 小程序 E2E（仅 Windows/Mac） | test-result.json |
| `npm run test:full` | 全量回归（unit+api+全部 e2e） | test-result.json |
| `npm run test:changed` | 仅跑本次变更相关测试（增量，依据改动说明「影响模块」筛选，见第 5 章） | test-result.json |

### 退出码规范（测试机据此判定）

| 退出码 | 含义 |
|--------|------|
| `0` | 全部通过（或全部跳过） |
| `1` | 存在失败用例（FAILED/ERROR） |
| `2` | 环境/参数错误（依赖缺失、配置错误）——此时判定为"环境问题"，不归咎于代码 |

所有测试执行统一输出一份 `test-result.json`（见第 7 章），**禁止各框架输出原始格式直接入库**。

## 7. 脚本输出规范（核心：test-result.json 统一格式）

所有测试（unit/api/e2e）最终必须归一为以下 JSON 结构，测试机据此入库和展示。

### 7.1 Schema

```json
{
  "schemaVersion": "1.0",
  "projectKey": "opc",
  "repoName": "opc-front",
  "branch": "main",
  "commitId": "a1b2c3d4",
  "runId": "20260819-101501-abc123",
  "runType": "CHANGED | NEW_FEATURE | REGRESSION | FULL",
  "startTime": "2026-08-19 10:15:01",
  "endTime": "2026-08-19 10:16:23",
  "env": {
    "os": "win32",
    "nodeVersion": "v20.11.0",
    "browser": "chrome-126",
    "wechatDevTools": "1.06.2405020"
  },
  "suites": [
    {
      "suiteName": "auth_login",
      "testType": "UNIT | API | E2E_WEB | E2E_MINIAPP | E2E_H5",
      "status": "PASSED | FAILED | SKIPPED",
      "durationMs": 1234,
      "cases": [
        {
          "caseId": "F-0301",
          "caseName": "登录_密码错误_提示文案正确",
          "status": "PASSED | FAILED | SKIPPED | ERROR",
          "durationMs": 120,
          "error": {
            "message": "expected '密码错误' but got ''",
            "stack": "at ...",
            "screenshot": "test/reports/screenshots/xxx.png"
          }
        }
      ]
    }
  ],
  "summary": {
    "total": 120,
    "passed": 115,
    "failed": 3,
    "skipped": 2,
    "durationMs": 82000,
    "failedCases": [
      { "suiteName": "auth_login", "caseName": "登录_密码错误_提示文案正确", "errorMessage": "..." }
    ]
  }
}
```

### 7.2 字段约束

| 字段 | 强制 | 说明 |
|------|------|------|
| `runId` | 是 | 每次执行唯一，测试机生成，用于追踪 |
| `runType` | 是 | 区分增量/全量，报表按此归类 |
| `commitId` | 是 | 必须与当前 pull 的 commit 一致 |
| `env` | 是 | 记录运行环境，排查"环境差异导致失败" |
| `suites[].cases[].caseId` | 是 | 关联测试规范条目（F-/UI-/D- 编号），可追溯 |
| 失败用例 `error.screenshot` | 失败时必填 | E2E 失败必须附截图，方便开发定位 |

### 7.3 输出落点

```
<repo>/test/reports/test-result.json     # 单次执行结果（gitignore）
/mydata/temp/test-results/<project>/<sha>/test-result.json   # 测试机汇总目录（与现有 publish-test-report.sh 约定一致）
```

### 7.4 与报告发布脚本的对接

`publish-test-report.sh` 读取 `test-result.json` 的字段映射：

| 报告字段 | 来源 |
|---------|------|
| `updatedFunctions` | 本次 commit 变更功能（取自改动说明「功能改动点」，见第 5 章） |
| `testedFunctions` | `suites[].suiteName` 去重 |
| `passedItems` | `summary.passed` |
| `failedItems` | `summary.failedCases` |
| `suggestions` | 失败归因建议（AI 分析失败日志生成） |
| `status` | `summary.failed == 0 ? PASSED : FAILED`（审计阻断时置 AUDIT_BLOCKED） |

## 8. 测试机执行规范

### 8.1 测试机环境要求

| 环境 | Web/接口（云端 Linux 可承载） | 小程序（必须 Windows/Mac） |
|------|------------------------------|---------------------------|
| Node | 固定版本（.nvmrc/node_version 锁定） | 同左 |
| 浏览器 | Chromium/Chrome 固定版本 | — |
| 微信开发者工具 | — | 固定版本 + 保持登录态 |
| 数据库/Redis | 独立测试库，可重建 | 同左 |
| 依赖 | 按 lock 文件安装 | 同左 |

### 8.2 执行步骤（测试机脚本固定顺序）

```bash
# 1. 拉取（版本对齐）
git fetch origin
git checkout <目标 commit>
git pull

# 2. 安装依赖（lock 文件，禁止 update）
npm ci

# 3. 重置测试环境
#    - 重建测试数据库（DROP + 迁移脚本重跑）
#    - 清 Redis 缓存
#    - 清测试数据目录

# 4. 按执行策略跑测试（见 8.3）

# 5. 汇总输出 test-result.json → 调用报告发布脚本（publish-test-report.sh）
```

### 8.3 执行策略

| 场景 | 策略 | 命令 |
|------|------|------|
| 每轮 push | 增量：依据改动说明「影响模块」只跑本次变更相关测试（见第 5 章） | `npm run test:changed` |
| 每日 | 常规回归：全量 unit + api | `npm run test:full -- --skip-e2e` |
| 发版前 | 全量回归：unit + api + 全部 e2e | `npm run test:full` |
| 小程序变更 | 额外跑小程序 e2e（仅专机） | `npm run test:e2e:miniapp` |

### 8.4 失败处理规范

| 判定 | 处理 |
|------|------|
| 失败用例中 50% 以上同一模块/同一断言 | 先怀疑测试脚本问题（选择器失效/数据未清），由开发修脚本 |
| 失败用例集中在环境相关（超时/截图为空） | 判定环境问题，重跑一次确认 |
| 同一用例连续两次失败且与环境无关 | 判定真实缺陷，阻断合入 |

## 9. 版本与对齐规则（底线）

| 编号 | 规则 |
|------|------|
| S-0801 | 测试机只认最新 commit，禁止用旧 commit 跑新代码 |
| S-0802 | 测试脚本与业务代码必须同 commit 提交，禁止分开提交 |
| S-0803 | 分支策略：测试结果只对当前分支有效，合入主干需主干重跑 |
| S-0804 | 测试机环境升级（Node/浏览器/开发者工具）必须在文档登记并全量回归一次 |

## 10. 反馈闭环

```
测试失败
   ├─ 失败信息 + 截图 + 日志 → 自动通知开发（企微/飞书/邮件）
   ├─ 开发定位：环境问题 → 测试机重跑；脚本问题 → 修脚本再 push；代码缺陷 → 修代码再 push
   └─ 修复后回到第 1 章流程循环
```

通知内容必须包含（供开发直接定位）：

```
项目 / 分支 / commit / 测试模块 / 失败用例名 / 失败断言信息 / 截图路径 / 环境信息
```

## 13. 完整示例（AI 生成脚本的参考样板）

> 本节提供一套**可直接照抄结构**的完整示例：Web E2E（Playwright）+ 接口测试 + 小程序 E2E（miniprogram-automator）。
> AI 生成脚本时的标准流程：**读取需求 + 读取《自动化测试规范总纲》相关条目 + 读取本规范 + 读取被测页面代码 → 按本节样板输出脚本。**

### 13.0 AI 生成脚本所需输入材料

| 输入 | 来源 |
|------|------|
| 本次改动说明 | `docs/changelogs/YYYY-MM-DD-<功能短名>.md`（S-0501，必读） |
| 适用规范条目 | 《自动化测试规范总纲》中 F-/UI-/D- 对应编号 |
| 交付规范 | 本规范（目录/命名/输出格式） |
| 被测页面/接口代码 | 仓库代码（确认 data-testid、组件类型、接口契约） |
| 测试环境配置 | `test/config/env.test.example` |

### 13.1 示例 A：Web 端 E2E（Playwright + TypeScript）

#### 目录与文件

```
test/e2e/web/
├─ auth_login_failed.test.ts          # 用例文件
├─ order_payment_timeout.test.ts
└─ support/
   ├─ apiClient.ts                    # 接口直连工具（造数/清理）
   └─ fixtures.ts                     # 测试账号/数据工厂
```

#### 用例文件（完整样板）

```ts
// test/e2e/web/auth_login_failed.test.ts
import { test, expect, Page } from '@playwright/test'
import { createTestUser, cleanupTestUser } from './support/fixtures'

// 对应规范：总纲 F-0301~F-0310（登录注册）、UI-0701（键盘类型）
// 命名：模块_功能_场景_预期
test.describe('登录_密码错误', () => {
  let testUser: { email: string; password: string }

  test.beforeAll(async () => {
    // 前置：通过接口直连造数（S-0305 数据自建）
```

```ts
import { writeFileSync } from 'node:fs'

export function toTestResult(raw: PlaywrightResult, meta: Meta): TestResultJson {
  const suites = raw.suites.map((s) => ({
    suiteName: s.title,
    testType: 'E2E_WEB',
    status: s.failures ? 'FAILED' : 'PASSED',
    durationMs: s.duration,
    cases: s.cases.map((c) => ({
      caseId: c.annotations.find((a) => a.type === 'caseId')?.description || '',
      caseName: c.title,
      status: c.failures ? 'FAILED' : 'PASSED',
      durationMs: c.duration,
      error: c.failures?.[0] ? {
        message: c.failures[0].message,
        stack: c.failures[0].stack,
        screenshot: c.attachments?.find((a) => a.name === 'screenshot')?.path, // 失败必截图
      } : undefined,
    })),
  }))

  const summary = { /* 汇总 total/passed/failed/skipped，见第 7 章 */ }
  writeFileSync('test/reports/test-result.json', JSON.stringify({ ...meta, suites, summary }, null, 2))
}
```
